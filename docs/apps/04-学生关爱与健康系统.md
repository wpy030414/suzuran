## 1. 文档概述

### 1.1 编写目的

本文档是「安徽钉钉学校」学生关爱与健康系统的产品需求文档，编写目的包括：

1. **完整描述产品需求**：以逆向自 4 个宜搭应用实际运行代码（页面 JS 业务逻辑源码）的第一手材料为基础，精确还原系统当前真实承载的业务流程、数据模型与规则，作为产品事实基线（Baseline）。
2. **回答"为什么"**：阐述每个功能解决什么问题、解决谁的问题，为后续迭代、重构与平台迁移（Suzuran Cloud）提供价值锚点，避免"只迁移表单、丢失业务语义"。
3. **作为验收与测试依据**：第 9 章验收标准可直接转化为测试用例的输入。
4. **作为隐私合规审查输入**：本系统涉及学生心理数据、家庭信息、健康记录等敏感个人信息，本文档第 5 章与第 6 章为合规评审提供依据。

本文档**描述"做什么"，不规定"怎么实现"**；现有宜搭实现中的技术细节（如 QuickMap ORM、Infection SDK）仅作为业务规则的佐证材料出现在附录或规则说明中，不构成对新实现的约束。

### 1.2 项目范围

本系统覆盖学生在校期间的**身心健康管理与关怀**全场景，由 4 个应用构成：

| 应用 | appType | 页面数 | 字段数 | 定位 |
|------|---------|--------|--------|------|
| 关爱特殊学生 | `APP_B2YISMBZS1VSSEDRQ0QL` | 14 | 69 | 特殊学生"一人一案"包保关爱的全生命周期管理 |
| 心理测试 | `APP_UIOTX081CDRCWZM529HW` | 27 | 59 | 面向全体师生的心理健康问卷测评 |
| 晨午检 | `APP_IB7HT0LU72CX84NEMKG8` | 10 | 55 | 每日晨午健康检查与缺勤/传染病追踪 |
| 分班查询 | `APP_VIGULR5BVOISHP5MRCGF` | 3 | 17 | 新生分班结果的对外查询发布 |

四者关系：**心理测试**筛查出的需要关注的学生可进入**关爱特殊学生**建档体系；**晨午检**负责日常生理健康监测与缺勤闭环；**分班查询**服务于学期初的组织准备。三者共同支撑学校"身心健康零遗漏"的管理目标。

**不在本系统范围内的能力**（Non-Goals）：

- 教师考勤与教师请假（属于行政办公系统）；
- 课程、课表、选课（属于课程管理系统）；
- 学生综合素质评价、学科评价（属于教师评价与考核系统）；
- 心理咨询预约、咨询记录管理（当前系统不承载，未来可作为扩展）；
- 医院/疾控直报（传染病上报目前仅在校内留痕，不与外部系统对接）。

### 1.4 术语与缩略语

| 术语 | 定义 |
|------|------|
| 包保 | 源自"包保责任制"：为每名特殊学生指定固定的责任教师（包保负责人）与责任领导（包保领导），一对一负责其关爱工作 |
| 关爱级别 | 对特殊学生的关注分级。每个级别定义关爱周期（月/学期）与周期内应完成的关爱次数 |
| 关爱周期 | 计划执行的时间口径，分"月"与"学期"两种。月计划按自然月统计，学期计划按学年学期统计 |
| 关爱登记 | 一次具体关爱动作（谈心、家访、辅导等）的执行记录，是核销计划次数的唯一凭证 |
| 暂缓关爱 | 包保教师发起的、经年级组长审批的"本周期内撤销对某学生关爱安排"的流程 |
| 学年 / 学期 | 系统内时间口径。学年形如"2025-2026学年"；一学年两学期，第 1 学期自 8 月 25 日起，第 2 学期自次年 2 月 1 日起（由内置学年引擎自动推算） |
| 问卷库 | 心理测评题目的资源库，题目按"问题组"组织，每题标注维度与正/负面性质 |
| 问题组 | 问卷库中一组题目的集合，是发放问卷的最小单元 |
| 游标 | 问卷库的全局发放指针（单例数值），参与人通过游标值取模确定其收到的问题组 |
| 轮次 | 一次测评活动的发放单位。轮次飘移指通过调整游标让同一批参与人在不同时间段获得不同问题组的机制 |
| 晨午检 | 每日上午（晨检）与下午（午检）两次对学生健康与出勤的例行检查 |
| 记名 / 记数 | 晨午检的两种学生记载模式：记名=按班级名单逐人勾选；记数=只报缺勤人数并对缺勤者逐一登记 |
| 半天时间窗 | 晨午检请假的时间粒度：以上午/下午为最小单位（HalfdayDatetime 语义） |
| autoLock | 晨午检学生行的自动锁定标记：该学生存在覆盖当前检查时段的有效请假时，其"情况"不可被班主任改动 |
| 级部 | 学校与年级之间的管理层级（一个校区可含多个级部），晨午检负责人体系的第三层 |
| 解禁日期 | 分班查询结果的生效时间，在此之前查询结果不对外展示 |
| 宜搭（Yida） | 钉钉低代码平台，本系统的现行载体 |

## 2. 产品愿景与定位

### 2.1 背景与问题陈述

中小学学生健康管理长期存在四类痛点：

1. **特殊学生关爱"有名单、无过程"**。上级督导要求学校对心理异常、家庭变故、行为偏差等特殊学生建立"一生一案"，但纸质台账难以证明关爱真实发生、频次达标、责任到人；检查时突击补材料成为常态。
2. **心理筛查"测了白测"**。问卷发放靠纸质或第三方平台，结果散落在 Excel，无法与校内学生档案联动，异常学生缺少后续跟踪入口。
3. **晨午检"填了白填"**。纸质晨检表无法汇总，缺勤原因不清；传染病病例无时间线，班主任请假审批与健康台账两张皮，同一学生信息要在两套系统里重复登记。
4. **分班发布"问讯爆炸"**。新生分班结果公布当天，家长围堵校门、电话打爆教务处，信息发布渠道单一且不可验证身份。

本系统以钉钉为宜搭底座，将上述四件事全部线上化、闭环化、责任化：**每一名特殊学生有人包保、每一次关爱有记录可查、每一天晨检有数据汇总、每一名缺勤学生有原因闭环、每一名新生家长可自助查证分班结果**。

### 2.2 目标用户画像

| 画像 | 描述 | 核心诉求 |
|------|------|----------|
| 校长 / 分管校长 | 全校学生安全第一责任人 | 一屏看清：哪些班级没报计划、哪些学生关爱没做完、今天有多少缺勤与传染病 |
| 心理教师 | 学生部专兼职心理教师，系统内的"专业权威" | 掌握问卷库与测评节奏；能跨班级组建/调整关爱计划；异常个案能快速定位 |
| 年级组长（年级主任） | 本年级关爱与晨午检的枢纽 | 督促各班按时上报；审批暂缓关爱；掌握本年级动态 |
| 班主任 | 班级的直接责任人，晨午检第一执行人 | 填写负担最小（名单自动带出、请假自动回填）；完成即可留痕 |
| 包保负责人（责任教师） | 一对一负责某特殊学生的教师 | 首页直接看到"我还欠谁几次关爱"，一键登记 |
| 包保领导 | 对特殊学生关爱负领导责任的中层/校级干部 | 被关联在档案上，可被追溯 |
| 家长 / 学生 | 新生家庭；部分场景下的在读学生 | 不下载 App、不登录内网即可自助查询分班；查询结果可信 |
| 系统管理员（王鹏宇等） | 应用搭建与维护者 | 基础数据（年级、班级、负责人、级别、时间）集中配置 |

### 2.3 核心价值主张

> **让"关爱"从一句口号变成可度量、可追责、可持续的组织行为；让"健康"从一次检查变成每天自动闭环的数据流。**

分解为四条价值线：

1. **责任到人（包保制数字化）**：学生基础信息中"包保负责人 + 包保领导"双字段，使每个特殊学生的关爱责任在系统内可被唯一定位；首页按登录人聚合待办，"谁的孩子谁抱走"。
2. **过程留痕（关爱即凭证）**：计划次数与登记次数在系统内自动轧差，"应做 N 次、已做 M 次、剩余 N-M 次"实时可见；图片上传支持关爱过程佐证。
3. **健康闭环（检查—请假—销假三位一体）**：晨午检发现异常自动生成请假流程；有效请假在下次检查中自动回填并锁定；销假可提前结束请假区间，传染病销假强制提交复学材料——出勤与健康数据天然一致。
4. **发布自助（零人工答疑）**：分班查询以"姓名 + 身份证号"双因子自助验证，配合解禁日期实现定时发布，教务处不再接听查询电话。

### 2.4 成功指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 班级计划上报率 | 每周期（月/学期）已提交关爱计划的班级数 / 全校班级总数 | ≥ 95% |
| 关爱完成率 | 每周期已完成的关爱登记次数 / 计划应关爱次数 | ≥ 90% |
| 晨午检按时上报率 | 在检查时间窗口内提交的检查记录 / 应提交的检查记录 | ≥ 98% |
| 缺勤闭环率 | 有有效请假或销假记录的缺勤学生 / 缺勤学生总数 | 100% |
| 传染病病例追踪完整率 | 有完整"发现—请假—复课材料"链路的传染病病例占比 | 100% |
| 分班查询人工介入率 | 需人工答复的分班咨询 / 分班咨询总量 | ≤ 5% |
| 心理测评覆盖率 | 实际提交问卷人数 / 应测人数 | ≥ 95% |
| 数据导出可用性 | 三个关爱看板均支持一键导出 | 100% 场景可用 |

## 3. 用户场景分析

### 3.1 场景一：校长在行政会上调出关爱台账（校长）

行政会前，校长打开"每周期学生关爱次统计"看板，选择"月 + 本月"，一眼看到每个包保学生的"应关爱次数 / 已完成次数"。发现某班 3 名学生完成率 50%，校长点击"一键提醒"，系统向未完成的包保教师批量写入提醒"请尽快完成本周期对 ×× 的关爱！（剩余 N 次）"。会后校长用"每周期班级计划上报情况"看板核对还有哪几个班没交下月计划，当场点名。

**价值**：管理动作从"问人"变成"看数"，督导压力精准传导到责任人。

### 3.2 场景二：心理教师组织一轮全员心理测评（心理教师）

开学第三周，心理教师发起一轮测评。系统在"轮次飘移"机制下自动推进全局游标，使本次发放的问题组与上学期不同（同一题库下轮换覆盖面）。学生打开"问卷填写"，系统按游标确定问题组，隐去题目维度与正负面性质（避免作答倾向），学生逐题选"是/否"，总分实时计算。提交后，心理教师在"问卷填写-审阅"报表中按总分排序筛查高分/低分个体，结合维度分布确定需要关注的学生名单，并将重点学生转入"关爱特殊学生"建档。

**价值**：测评组织成本趋近于零；结果天然结构化，可追踪、可比对、可联动关爱体系。

### 3.3 场景三：班主任的晨检五分钟（班主任）

早读前，班主任打开"检查"页，选好班级，学生名单自动带出（记名模式）。两名学生没到：张三发烧（班主任标注"异常-发热"），李四昨天已请假（系统自动回填其请假信息并锁定该行，班主任无需也不得改动）。张三的异常在提交时自动生成一条从"今日上午"开始的请假流程实例，代理人默认填班主任自己——后续由李四家长或班主任补齐请假信息。应到 45、实到 43、缺勤 2 自动算出。下午午检同理。

**价值**：一次填写同时完成健康台账 + 缺勤台账 + 请假发起三件事，无重复录入。

### 3.4 场景四：包保教师完成一次谈心并登记（包保负责人）

包保教师登录后，首页"待关爱"区显示：学生王五，本周期还应关爱 2 次。点击"去关爱"跳转登记页，关爱对象已自动带入王五。谈心结束后，教师选择关爱形式（如"谈心谈话"）、填写内容、拍照上传。提交后，首页该学生的剩余次数减 1。

**价值**：关爱动作即登记，剩余次数实时轧差，教师始终知道自己"欠不欠账"。

### 3.5 场景五：学生情况好转，教师申请暂缓关爱（包保负责人 + 年级组长）

学生赵六经过一学期干预已明显好转。包保教师在首页对赵六点击"暂缓关爱"，系统两次确认（"等效于在计划中撤销对其的关爱""审批通过后不可撤销"），教师输入理由后发起流程；系统自动将赵六所在年级的年级组长设为审批人，并携带本周期计划全量快照。年级组长审批同意后，计划表中赵六的"本周期检查"勾选被清除——该生本周期不再产生应关爱义务。

**价值**：关爱资源从"只进不出"变为可动态调整，同时保留审批留痕，防止随意甩包袱。

### 3.6 场景六：家长查询新生分班（家长 / 学生）

8 月 30 日（解禁日期），新生家长扫描学校公众号里的二维码进入"分班查询"页，输入孩子姓名与身份证号，点击查询。结果页显示：校区、班级与一张二维码图片（扫码进班级群）。若查询时间在解禁日期之前，结果不予展示；输入不匹配则查无此人。

**价值**：身份双因子验证防止他人冒查；解禁机制让学校掌握发布节奏；零人工成本。

### 3.7 场景七：传染病病例的完整追踪（班主任 + 校医 + 管理员）

晨检中学生孙七被标注"异常-传染病"并选择传染病类型（如"流行性腮腺炎"），提交时自动生成请假流程。孙七连续请假一周，期间每天的晨检都会自动回填该请假并锁定孙七行。一周后孙七返校，班主任发起销假，选择该请假记录：因情况含"传染病"，系统强制要求上传复学材料（医院复课证明），销假提交后请假流程实例的结束时间被更新为实际返校时间。"检查概要 / 缺勤概要"报表全程留痕，校医可据此统计传染病时间线。

**价值**：传染病从发现到复课的全链路在系统内自动串联，满足疾控要求的可追溯性。

### 3.8 场景八：管理员的新学期初始化（管理员）

新学期开始，管理员依次完成：在晨午检中维护"学校/校区/级部—年级—班级（负责人）"三级负责人树与班级学生名单（选择学生记载模式：记名/记数）、配置检查时间段；在关爱特殊学生中维护年级（年级主任）、班级（班主任）、关爱级别（类型 × 周期 × 次数）；在心理测试中核对组织架构（教师、学生、班级、办公室）与时间段；在分班查询中导入新生分班信息并设定解禁日期。

**价值**：所有基础数据一处配置、全局生效，学期中无需再动结构数据。

### 4.1 子系统一：关爱特殊学生（GA）

#### 4.1.1 功能概述

本子系统的使命是把"一生一案"从纸面台账变成**闭环生命周期**：

```
建档（学生基础信息）
  → 定级（关爱级别：类型 × 周期 × 次数）
  → 计划（班主任按周期上报 / 心理教师跨班统管）
  → 执行（关爱登记，核销计划次数）
  → 跟踪（首页待办 + 三个统计看板 + 一键提醒）
  → 暂缓 / 终止（年级组长审批，回写计划）
```

**双轨角色设计**是本子系统最重要的产品决策：

- **普通教师（班主任）轨道**：只能为本班生成计划。提交前系统校验"你是否该班班主任"，非班主任不得以普通教师身份提交。
- **心理教师轨道（LEADER）**：通过"心理教师"名单表校验身份后，可在计划中**自由增删学生、调整包保责任人**（学生表"姓名"与"包保责任人"两列对心理教师可编辑，对普通教师只读）。该机制支撑心理教师跨班级统筹个案——例如把某学生的包保责任从班主任移交给专职心理教师。

**计划与执行的轧差口径**：应关爱次数来自计划行（`本周期检查次数`），已完成次数来自关爱登记记录，两者在首页与看板实时轧差得出剩余次数。月计划按自然月窗口轧差，学期计划按整个学期轧差。

#### 4.1.5 业务规则与流程

**规则 GA-R1（计划生成口径）**：班主任上报计划时，系统按"年级 + 班级"检索学生基础信息，仅纳入**关爱级别的周期口径与本次计划周期类型一致**的学生（例如级别关爱周期为"学期"的学生不出现在月计划中）。每个学生的默认次数 = 关爱级别配置表中的"周期次数"。

**规则 GA-R2（身份校验）**：发起人身份为"普通教师"时，若"班级"字段为空（即登录人不是任何班级的班主任），提交被拦截并提示"您不是班主任，不可以以普通教师的身份提交！"。发起人身份为"心理教师"时，登录人必须存在于"心理教师"名单表中。

**规则 GA-R3（轧差口径）**：对某学生 S 与某计划 P（周期类型 t）：

- 已完成次数 = 关爱登记中（关爱对象 = S，关爱教师 = 计划行责任人所在统计视图，学年学期匹配 P 的学年学期）且满足时间窗口的记录数；时间窗口：t = 月 → 登记日期落在 P 的月份自然月内；t = 学期 → 无额外日期限制（整个学期内均可核销）。
- 剩余次数 = P 的"本周期检查次数" − 已完成次数。
- 仅统计"本周期检查"勾选的计划行；仅统计有关联学生实例的行。

**规则 GA-R4（首页待办归属）**：首页"待关爱"仅展示**包保责任人为登录人**的计划行（未指定责任人或责任人为他人的行不展示）。

**规则 GA-R5（暂缓审批语义）**：暂缓等效于"在本周期计划中撤销对该学生的关爱"，而非"清零剩余次数"。审批通过后，系统将预生成的学生明细快照（目标学生勾选已清除）整体回写至 PlanUUID 对应的计划实例，**不可撤销**。审批人由系统按学生所在年级的年级主任自动指派。

**流程 GA-F1（月度关爱闭环）**：

```
月末：班主任/心理教师提交下月计划（FR-GA-03/04）
  ↓ 学生部/管理员通过看板 FR-GA-08 核查上报率
月初～月末：责任人执行关爱并登记（FR-GA-05）
  ↓ 首页 FR-GA-06 实时显示剩余次数
月末：管理员通过 FR-GA-10 核查完成率，对未完成者 FR-GA-11 一键提醒
  ↓ 个别好转学生走 FR-GA-07 暂缓
进入下月周期
```

**流程 GA-F2（暂缓关爱）**：

```
首页对目标学生点击"暂缓关爱"
  → 确认框 1：警示"等效于撤销本周期关爱，非清零"
  → 确认框 2：警示"学生部审核，通过后不可撤销"
  → 输入理由（取消则终止）
  → 系统定位学生年级 → 取年级主任为审批人
  → 生成计划学生明细快照（目标学生勾选清除、责任人字段转 ID 格式）
  → 发起暂缓关爱流程
  → 年级组长审批：同意 → 快照整体回写计划表；拒绝 → 计划不变
```

**流程 GA-F3（看板刷新）**：三个看板共享统一的筛选器交互——周期类型切换为"月"时显示"指定月份"、隐藏学年学期；切换为"学期"时显示学年学期、隐藏月份；默认当前月/当前学年学期。点击查询后并行拉取基础数据与计划数据，在浏览器内关联计算后渲染表格（动态摸排与次数统计额外提供搜索框与导出按钮）。

### 4.2 子系统二：心理测试（XL）

#### 4.2.1 功能概述

本子系统的使命是以最低运营成本支撑**周期性、全员性、可轮换**的心理健康测评。其三大独特机制（均由业务代码实证）：

1. **问卷库 + 问题组**：题目不以"整卷"为单位管理，而是按"问题组"组织。每组含若干题，每题标注**维度**（测评维度）与**性质**（正面 / 负面）。同一题库可切出多组题目，轮换使用。
2. **游标发放**：全局单例数值（游标表）。填写页加载时读取游标值 `p`，填写人实际拿到的问题组 = `|p| mod 问题组总数`。即游标每推进一次，全体参与人拿到的问题组整体轮换一档。
3. **轮次飘移**：轮次飘移表在每次推进时快照"日期时间 + 当前游标 + 自动化标记"，形成轮次审计轨迹。学期更替时通过调整游标让测评内容自然"飘移"到新问题组，无需重新组卷。

**盲测设计**：填写页中题目的"维度"与"性质"两列对填写人**隐藏**（HIDDEN），防止学生揣摩"答什么是好答案"；总分实时计算但对填写人仅呈现数字，不呈现解释。

**计分规则**：总分 = 正面题答"是"的题数 + 负面题答"否"的题数。即总分度量的是"与积极心理状态一致的作答数"，低分提示需要关注。

**组织架构底座**：本应用内嵌一套与"教师考核"同构的组织架构表（教师、学生、空间、年级、班级、广义办公室、教师职务、学生职务、时间段、周行事件，各配管理视图），支撑"按年级/班级/办公室定向发放"的人员圈选能力，并为后续向平台迁移提供实体基线。

**规则 XL-R1（发放确定性）**：给定游标值 p 与问卷库问题组集合 Q（按查询顺序），填写人获得的问题组为 `Q[|p| mod |Q|]`。同一游标值下所有填写人获得同一问题组；游标推进 1，全体轮换一档。

**规则 XL-R2（答卷快照）**：填写页加载问题时将问卷库题目**复制**进答卷（维度、性质、问题），答卷与题库解耦——此后题库修改不影响已交答卷。

**规则 XL-R5（成员指针自动带出）**：录入教师/学生时选择成员后，识别符（成员 ID）与名称文本自动回填。

```

```

**流程 XL-F2（学期轮次飘移）**：新学期测评前，管理员推进游标 k 档（k ≥ 1），使本轮问题组与上学期不同；每次推进落一条轮次飘移记录（日期时间 + 推进后游标值 + 自动化标记），形成可审计的轮次历史。

### 4.3 子系统三：晨午检（CJ）

#### 4.3.1 功能概述

本子系统的使命是**每日两次、逐级汇总、缺勤全闭环**的健康监测。三大结构性设计：

1. **负责人层级体系**：学校/校区/级部 → 年级 → 班级三级负责人树。班级是叶子节点，携带学生名单与"学生记载模式"；检查页按"检查人 = 班级负责人"匹配出该检查人名下的班级。级部负责人可以跨级部检查（负责人字段决定可见班级集合）。
2. **双记载模式**：记名（按名单逐人勾选，应到/实到/缺勤自动计算）与记数（只填缺勤人数，应到取班级配置的"学生数量"，缺勤几人就展开几行登记谁缺勤）。模式在班级配置页设定，检查页自动遵循。
3. **检查—请假—销假三位一体**：检查提交时，未请假的异常学生自动生成请假流程实例；已有有效请假的学生在检查页自动回填并锁定；销假可以提前结束请假区间并对传染病病例强制复学材料。三者共享同一份"半天时间窗"时间语义（上午/下午为最小粒度）。

**半天时间窗（HalfdayDatetime）**是全子系统的时间基元：一个时刻 = 日期 + 半日（上午/下午），可比较、可构成区间、可判断包含。晨检对应"上午"、午检对应"下午"。请假区间 [从日期+从时间, 至日期+至时间] 覆盖检查时点即视为有效请假。

#### 4.3.5 业务规则与流程

**规则 CJ-R1（班级可见域）**：检查页"班级"下拉的选项 = 所有"负责人 = 登录人"的班级（可跨校区/级部/年级）。选择班级后，学校/校区/级部、年级文本自动带出。

**规则 CJ-R2（模式切换）**：页面轮询（约 500ms）检测"记载模式 + 学生明细 + 缺勤数"组合是否变化，变化时执行模式适配：

- **记名模式**：应到 = 名单行数；实到 = 情况为"正常"的行数；缺勤 = 非正常行数；学生明细"名称/性别"只读（名单为准）。
- **记数模式**：应到 = 班级配置的"学生数量"；实到 = 应到 − 缺勤（手填）；缺勤 > 0 时展开明细，行数适配缺勤数（不足补齐、超出截断），明细"名称/性别"可编辑（谁缺勤由教师补充）；缺勤 ≤ 0 时隐藏明细。

**规则 CJ-R3（有效请假判定）**：请假区间 [从日期+从时间, 至日期+至时间]（半天粒度）覆盖检查时刻（检查日期 + 晨检→上午 / 午检→下午）时，该请假对该学生本次检查有效。区间端点闭区间判定。

**规则 CJ-R4（自动回填与锁定）**：检查页加载（及刷新）时，对明细中每名学生查询请假流程实例：命中有效请假 → 该行置 `autoLock` 标记，且"情况 / 传染病类型 / 备注"回填为该请假记录的对应字段，并禁用编辑（防止班主任篡改或重复登记）；未命中 → 行保持可编辑且清空残留值。回填查询受并发锁保护（同一时刻仅一个回填任务执行），避免竞态。

**规则 CJ-R5（异常自动请假）**：检查提交后，对明细中**未锁定且情况 ≠ 正常**的每一行，自动创建一个请假流程实例，字段映射：班级上下文（校区/级部/年级/班级）、代理人 = 检查人、姓名/性别/情况/传染病类型/备注 = 该行值、从日期 = 至日期 = 检查日期、从时间 = 至时间 = 晨检→上午 / 午检→下午。即**一次异常检查 = 一次请假发起**，缺勤台账与请假台账在数据层天然一致。

**规则 CJ-R6（销假提前结束）**：销假提交时，将所选请假流程实例的"至日期"与"至时间"更新为销假页的结束时间/结束时间段。销假仅影响区间终点，不删除流程实例（留痕）。

**规则 CJ-R7（传染病复学材料）**：销假页选中请假记录后，若其"情况"含"传染病"，则"复学材料"附件字段激活（必填），否则保持隐藏。

**流程 CJ-F1（一次晨检（记名模式））**：

```
班主任打开检查页 → 选班级（负责人匹配）
  → 日期禁用为当日，时间段选晨检
  → 页面轮询模式 → 名单带出，应到/实到/缺勤自动计算
  → 回填任务：对每个学生查询有效请假 → 命中行锁定+回填，未命中行可编辑
  → 教师对未锁定行标注情况（异常 → 可选传染病类型）
  → 提交 → 对未锁定且异常的行自动生成请假流程实例
```

**流程 CJ-F2（传染病全链路）**：

```
晨检发现异常 → 标注"异常-传染病"并选择类型 → 提交自动生成请假流程实例
  → 后续每日晨/午检自动回填该请假（区间覆盖即锁定）
  → 病情好转 → 班主任销假：选中该请假记录 → 因含"传染病"强制上传复学材料
  → 销假提交 → 请假区间终点更新为返校时点
  → 检查概要/缺勤概要中该病例全程留痕
```

**流程 CJ-F3（缺勤闭环核对）**：各级负责人通过检查概要（按管辖范围）核对"应检班次数、已报班次、缺勤总数、传染病数"，对未报班级督促；缺勤概要核对每名缺勤学生的请假/销假状态，确保闭环率 100%。

### 4.4 子系统四：分班查询（FB）

#### 4.4.1 功能概述

本子系统解决开学季最典型的"问讯风暴"问题：分班结果发布当天的家长查询洪峰。产品策略是**让家长自助、让系统守时、让结果可信**：

- **自助**：家长仅需姓名 + 身份证号两个自然信息即可查询，无需登录、无需下载任何应用；
- **守时**：分班信息记录带"解禁日期"，查询页对未到解禁日期的记录不展示结果（服务端时间校验 + 页面行为双保险）；
- **可信**：身份证号双因子校验防止他人冒查；结果页同时展示校区、班级与班级群二维码图片（由超链接字段驱动渲染），家长扫码即可进群，进一步降低人工答疑。

表单字段设计使"分班信息"（导入源）与"分班结果"（发布视图）共享同一套字段骨架，导入 → 发布全流程字段零映射。

#### 4.4.2 页面清单

| # | 页面 | 类型 | 说明 |
|---|------|------|------|
| 1 | 分班查询 | display | 查询入口：学生姓名 + 学生身份证号 → 校验非空 → 带参跳转结果页 |
| 2 | 分班结果 | receipt | 结果展示页（查询页带参直达；解禁日期限制展示；超链接渲染二维码图） |
| 3 | 分班信息 | receipt | 分班信息维护表（管理端导入源） |

#### 4.4.3 数据模型

**实体 1：分班信息 / 分班结果**（同构骨架，7~8 字段）

| 字段 | 类型 | 说明 |
|------|------|------|
| 学生姓名 | 文本 | 查询条件① |
| 学生身份证号 | 文本 | 查询条件②（双因子之一） |
| 校区 | 文本 | 展示 |
| 班级 | 文本 | 展示 |
| 备注 | 文本 | |
| 超链接 | 文本 | 班级群二维码图片地址（结果页渲染为图片） |
| 解禁日期 | 日期 | 展示门槛：`值 ≤ 当前时间` 才展示结果 |
| 富文本（仅结果页） | 富文本 | 结果说明区（由超链接驱动图片渲染） |

#### 4.4.4 功能清单

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| FR-FB-01 | 分班信息导入 | 管理员导入/维护分班信息（含解禁日期） | 必需 |
| FR-FB-02 | 双因子查询 | 姓名 + 身份证号非空校验后带参跳转结果页 | 必需 |
| FR-FB-03 | 解禁时限 | 未到解禁日期的查询不展示结果（值级时间校验） | 必需 |
| FR-FB-04 | 二维码展示 | 超链接字段渲染班级群二维码图片 | 期望 |
| FR-FB-05 | 结果核对 | 姓名/身份证号不匹配时查无结果 | 必需 |

#### 4.4.5 业务规则与流程

**规则 FB-R1（查询前置校验）**：查询页两个输入框任一为空时拦截并提示"姓名和身份证号不能为空！"，不发起跳转。

**规则 FB-R2（带参直达）**：校验通过后将姓名与身份证号作为 URL 参数传递给结果页，由结果页数据源按参数过滤记录。

**规则 FB-R3（解禁限制）**：结果页监听"解禁日期"字段值变化：`值 > 当前时间戳` 时置位限行状态（limit = true），结果不予展示；解禁日期到达后恢复展示。**注意**：该逻辑为字段值级行为，须配合服务端时间比较，避免前端时钟可被绕过（见第 5.2 节）。

**规则 FB-R4（二维码渲染）**：结果页"超链接"字段值变化时，将其作为图片地址渲染为页面内图片（班级群二维码）。

**流程 FB-F1（发布生命周期）**：

```
管理员导入分班信息（含解禁日期）
  → 解禁日期前：家长查询 → 校验通过但结果不展示（限行）
  → 解禁日期当天：管理员对外发布查询入口（公众号/公告）
  → 家长输入姓名+身份证号 → 校验 → 结果页展示校区/班级/二维码 → 扫码进群
  → 查询高峰过后，管理员可下架入口
```

| 能力 | 管理员 | 家长/公众 |
|------|:---:|:---:|
| 分班信息维护（含解禁日期） | ● | — |
| 查询与查看结果 | — | ●（无登录，双因子校验） |

### 4.5 公共机制：学年学期引擎（系统级）

本机制由关爱特殊学生应用的业务代码内置（Infection SDK 实证），心理测试与晨午检亦复用同类时间口径，定义如下：

| 规则 | 定义 |
|------|------|
| 第一学期起点 | 每年 8 月 25 日 0 时 |
| 第二学期起点 | 次年 2 月 1 日 0 时 |
| 基准学年 | 当前年份 −（当前时间 < 当年第一学期起点 ? 1 : 0） |
| 基准学期 | 当前时间 < 当年第二学期起点 或 当年第一学期起点 < 当前时间 → 第 1 学期；否则第 2 学期 |
| 学年显示 | "2025-2026学年"样式；学年选择器默认基准学年，可回退 6 年 |
| 学期显示 | "第1学期 / 第2学期"；默认基准学期 |
| 月计划窗口 | 自然月 [月初 0 时, 次月月初 0 时 − 1ms] |
| 半天语义 | 上午 = 12 点前（含）；下午 = 12 点后（不含）——用于晨午检时段映射与默认值 |

引擎的核心价值：**全校时间口径单点定义**，避免各应用各自拍脑袋选择"当前学期"，保证计划、登记、统计的跨应用一致性。

### 5.2 安全与隐私保护（学生敏感数据专项）

学生心理数据、健康数据、家庭信息属于《个人信息保护法》第二十八条规定的**敏感个人信息**，本系统按"最小化收集、按需可见、全程留痕、限期留存"原则管理。

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-S-01 | 身份认证 | 全员钉钉组织身份单点登录；分班查询为唯一的无登录公开入口，且以"姓名 + 身份证号"双因子约束 |
| NFR-S-02 | 最小可见性 | 班主任/包保教师仅可见本人负责的班级与学生；心理数据审阅仅限心理教师与管理员；任何人不经授权不可按姓名/班级浏览他人敏感信息 |
| NFR-S-03 | 字段级隐藏 | 测评填写页的"维度/性质"对填写人隐藏（盲测）；检查页未命中有效请假的明细行不得残留他人数据 |
| NFR-S-04 | 关键流程留痕 | 暂缓关爱审批（含计划快照）、轮次飘移（游标+时间）、销假（区间更新）三类操作必须可审计，记录操作人、时间、前后值 |
| NFR-S-05 | 导出管控 | 动态摸排/关爱次数看板导出受权限控制，导出文件不得超出操作人数据可见域；导出行为建议记录日志 |
| NFR-S-06 | 数据留存 | 敏感字段（监护人电话、住址、心理答卷、健康情况）按学校数据保留政策设定期限，超过期限不得继续对外可读（归档处理） |
| NFR-S-07 | 传染病信息 | 传染病类型数据仅在有真实业务需要（晨检填报、请假、销假、概要统计）的范围内展示 |
| NFR-S-08 | 解禁时限安全 | 分班结果的"解禁日期"判断必须以服务端时间（或可信时钟）为准，不得仅依赖前端时间（防改表/改时绕过） |
| NFR-S-09 | 传输与存储 | 所有数据访问走 HTTPS；敏感字段存储加密或访问受控（按宜搭平台安全基线执行） |
| NFR-S-10 | 未成年人特殊保护 | 学生（未成年人）敏感信息查询、导出、外发均需遵循学校内部审批；对家长公开的信息仅限分班结果（姓名、校区、班级、二维码） |

### 6.3 数据流向

1. **配置流向**：学年学期引擎与各级配置表（年级/班级/级别/负责人/时间）→ 计划、检查、测评等业务单据 → 看板/报表聚合展示。
2. **关爱数据流**：学生基础信息 → 计划（周期生成）→ 登记（核销）→ 首页/看板轧差 → 提醒（欠账推送）；暂缓审批将计划明细快照回写计划。
3. **健康数据流**：班级名单 → 检查明细（记名/记数）→ 异常行自动转请假实例 → 下次检查回填锁定 → 销假更新区间终点 → 概要报表汇总。
4. **测评数据流**：问卷库 + 游标（取模）→ 答卷快照 → 总分 → 审阅报表 →（研判后）转关爱建档。
5. **分班数据流**：分班信息（管理端导入）→ 查询入口（双因子）→ 结果页（解禁时限 + 二维码渲染）。

### 6.4 数据一致性约束

- 计划次数与登记次数的轧差为**派生数据**，不得独立落库（防双写漂移）；应/实/缺勤三数同理派生自明细。
- 暂缓审批的 DataJSON 快照必须与计划表行结构强一致，回写为**全量覆盖**语义（含未被暂缓的学生行），保证计划表不出现半更新。
- 销假更新请假区间终点为**原位更新**，同时保留流程实例的完整历史（审批链可见）。
- 同一学生同一天同一时段不得存在两条互相冲突的有效请假（半天时间窗校验）。

## 8. 约束与假设

### 8.1 约束

| 编号 | 约束 |
|------|------|
| CON-01 | 现行载体为钉钉宜搭低代码平台，页面 JS 受平台运行机制约束（成员/关联表单/流程的能力边界） |
| CON-02 | 统计看板的"应做/已做"轧差依赖关爱登记数据质量，登记缺失将造成口径偏差 |
| CON-03 | 晨午检两报表标注 `TO_REFACTOR`，当前统计能力受限，重构期间不得破坏数据写入路径 |
| CON-04 | 暂缓关爱一旦审批通过即不可撤销（产品决策，不可被审批人之外的角色绕过） |
| CON-05 | 分班解禁日期判断依赖可信时钟；匿名入口无法做到实名审计，仅双因子约束 |
| CON-06 | 数据保留期限与导出审计依赖学校平台管理规范落地，本系统提供字段与接口能力 |

### 8.2 假设

| 编号 | 假设 |
|------|------|
| ASS-01 | 每个班级配置一名负责人（班主任）；一名教师可负责多个班级或层级 |
| ASS-02 | 学生姓名在班级范围内唯一（晨午检记数模式与请假联动按姓名匹配） |
| ASS-03 | 关爱级别配置由学生部统一定义并保持稳定，学期中不频繁调整 |
| ASS-04 | 测评规模在全校 2000 人以内时按单游标全局发放即可满足轮换需求；规模扩大后需引入班级级游标 |
| ASS-05 | 家长查询分班时能提供准确身份证号；身份证号属于家长已知信息（新生报名时已采集） |
| ASS-06 | 传染病复学材料由学校校医/班主任把关上传，不自动校验医疗真实性 |
| ASS-07 | 平台迁移（Suzuran Cloud）后，钉钉组织架构继续作为人员与身份的唯一事实来源 |
