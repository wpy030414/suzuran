## 1. 文档概述

### 1.1 编写目的

本文档旨在完整、准确地描述「安徽钉钉学校」课程管理系统的产品需求，回答三个核心问题：

1. **解决什么问题**：学校在课表编排、日常调代课、选修课选课、体育课考勤、听评课教研五个环节中长期依赖纸质单据、Excel 表格与口头沟通，信息不互通、数据不沉淀、监管无抓手。
2. **解决谁的问题**：教导处管理员（排课与监管）、任课教师（查课与调代）、班主任与体育教师（考勤对账）、学生（查课与选课）、巡课与教研管理者（课堂质量把控）。
3. **做成什么样子**：以钉钉组织架构为底座，用五个宜搭应用构成「课表即数据、变动即流程、考勤即对账、教研即沉淀」的教学运行闭环。

本文档是产品设计、开发实现、测试验收与后续运维的共同契约；文中对业务规则的表述以逆向分析现有应用源码所得为准。

### 1.2 项目范围

本系统由五个宜搭应用组成，均部署于钉钉「安徽钉钉学校」组织内：

| 序号 | 应用名称 | appType | 启用状态 | 一句话定位 |
|-----|---------|---------|---------|-----------|
| 1 | 智能课表 | `APP_I2KGFFDDMKHO7Q7PTTR8` | 启用 | 课表全生命周期管理：基础配置、批量孵化、快照查询、调代课审批、巡课 |
| 2 | 省心课表 | `APP_WRJWKV4Q4LACDC0DYIJX` | **暂不启用** | 单页应用形态的轻量课表方案（实时计算模型），作为备用路线保留 |

**不在本系统范围内**（Non-Goals）：

- 不处理教师人事排班、工作量核算（属教师考核系统）；
- 不处理学生请假审批（属请假应用），但与其存在数据联动语义；
- 不做智能排课算法（冲突求解器）。「智能课表」的"智能"指自动化展开与数据联动，而非自动求解课表；
- 不做校外培训机构、家长端功能。

| 宜搭 | 钉钉低代码应用搭建平台（aliwork.com），本系统全部应用的承载平台 |

## 2. 产品愿景与定位

### 2.1 背景与问题

学校教学运行的日常痛点可归纳为五类：

1. **排课重、变更乱**。每学期排课以 Excel 完成，打印张贴；一旦有教师请假、会议冲突，调课代课靠微信群喊话，事后无人对账，经常出现"课表上写着 A 老师、教室里站着 B 老师、台账里查不到变更记录"的三头不一致。
2. **查课难**。教师想知道"我明天第几节有课"、代课教师想知道"这节课原来是谁的课"，都要翻纸质课表或问同事。
3. **选课乱**。课后服务选修课报名靠班主任代收纸质回执，容量控制靠人工数数，超员、漏报、同类型课程重复选等问题频发。
4. **体育考勤单点失真**。体育课在室外进行，点名由体育老师单方完成；学生若事先向班主任请假而体育老师不知情，就会出现"人没到、没人报"的静默缺勤，存在安全管理风险。
5. **教研无沉淀**。听课评课靠纸质听课本，听完即止，评分口径不一，学校层面无法统计听评课完成率，也无法沉淀教研资产。

### 2.2 产品定位

本系统定位为**学校教学运行的"事实源"**：让每一节课"在哪个班、第几节、谁在教"这件事有且仅有一个权威数据源，并让一切变更（调代课）、一切观察（巡课、听课）、一切核对（体育考勤）都发生在这个数据源之上。

核心设计哲学（自现有实现中提炼）：

- **课表即数据，而非图片**：课表被建模为结构化记录，可被查询、叠加、统计；
- **变动即流程**：调代课必须走确认/审批，私下调课在系统中不产生效力；
- **考勤即对账**：用两个独立信息源相互印证代替单方填报；
- **教研即沉淀**：听课、研讨、备课全部结构化入库，可统计、可回溯。

### 2.3 目标用户画像

| 角色 | 人群特征 | 核心诉求 | 典型场景 |
|------|---------|---------|---------|
| 教导处管理员 | 1-3 人，熟悉 Excel，不熟悉编程 | 一次性把学期课表灌进系统；变更可控；随时掌握课堂实况 | 学期初配置课表、孵化快照；学期中处理调代课审批、查看巡课记录 |
| 任课教师 | 全校数十至百人，移动端为主 | 一眼看到自己的课；换课少跑腿、不欠人情账 | 手机上查个人课表；发起/响应调课代课 |
| 班主任 | 兼任班级管理 | 学生请假后体育课那边也能知道 | 为请假学生填报体育课请假 |
| 体育教师 | 带多个班 | 点名快、请假信息自动到位 | 按班发起考勤，勾选到勤 |
| 学生 | 中小学生，由家长或本人操作 | 选到想上的选修课 | 在选课页浏览、选课、退课 |
| 巡课管理员 | 值班行政 | 巡课记录快、有图有真相 | 按节次拉出当节全部课程逐班巡查 |
| 教研组长/授课教师 | 听评课参与人 | 预约省事、评课有标准、记录不丢 | 发起听课预约、填写量表评课、参与研讨 |

### 2.4 核心价值主张

1. **一张活的课表**：从学期初到学期末，任何人任何时刻查到的课表都反映了全部已生效的变更；
2. **变更零丢失**：每一次调代课都有发起人、对象、时间、审批结论，可审计、可追溯；
3. **考勤双保险**：体育课缺勤不再依赖单一信息源，异常自动显性化；
4. **选课自助化**：容量与规则（90 分钟上限、同类型限一）由系统强制，管理员零人工干预；
5. **教研数字化**：听课完成率、评课得分、备课记录从"口头汇报"变为"报表呈现"。

### 2.5 成功指标

| 指标 | 基线（现状） | 目标 |
|------|-------------|------|
| 学期课表上线时长 | 开学后 1-2 周仍在变动 | 开学前 3 天内完成全部班级快照孵化 |
| 调代课留痕率 | 无法统计（微信群口头） | 100% 调代课在系统内留痕 |
| 课表查询准确率 | 纸质课表滞后，准确率不可知 | 与生效变更一致率 100% |
| 体育课异常发现时效 | 事后家长反馈才知晓 | 当日内在异常检测报表可见 |
| 选课超员次数 | 每学期数次 | 0（系统硬约束） |
| 听评课完成率可统计性 | 不可统计 | 报表按人/按周可查，任务完成率 ≥ 95% |

## 3. 用户场景分析

本章按角色给出典型场景。每个场景包含：场景描述、前置条件、主流程、异常流程、后置条件。

### 3.1 教导处管理员

#### 场景 S-01 学期初课表上线（智能课表）

- **场景描述**：新学期的第一周之前，教导处王老师需要把全校 48 个班的课表录入系统，让全校师生开学第一天就能查到准确课表。
- **前置条件**：王老师拥有智能课表管理员权限与课表孵化器口令；校区、班级、节次、科目、可索引教师五项基础数据已维护至最新（新增班级已录入、新入职教师已加入教师池）。
- **主流程**：
  1. 王老师逐一核对「校区」「班级」「节次」「科目」「可索引教师」五张基础表；
  2. 为每个班级新建一条「课表」记录：选择校区、班级、学期范围（起止日期），在自动生成的节次行（按节次优先级排序）中填写周一至周日的科目与授课教师；
  3. 打开「课表孵化器」，输入口令解锁；
  4. 点击「生成」，系统遍历全部课表记录，将每条课表按学期范围逐日展开为快照，页面实时显示进度（已完成/总数）；
  5. 生成完成后，王老师在「首页」抽查若干班级与教师的当周课表，确认无误；
  6. 通知全校师生系统可用。
- **异常流程**：
  - A1：某节次漏填教师 → 该日该节次不生成快照，首页对应格子为空，王老师补充课表后重新孵化（需先清理旧快照，见 A2）；
  - A2：需要重跑孵化（如发现学期范围填错）→ 使用孵化器的「清理快照」功能分批删除既有快照（每批 100 条循环删除并显示进度）后重新生成；
  - A3：生成过程中浏览器卡顿 → 孵化为串行批量写入，建议保持页面焦点直至 toast 提示"已完成"。
- **后置条件**：全校当学期快照就绪；首页可按校区/班级或教师维度查询；巡课、调代课功能可用。

#### 场景 S-02 审批调代课（智能课表）

- **场景描述**：数学李老师下周二要参加区里教研，请同组赵老师代两节课，在系统中发起代课申请，王老师审批。
- **前置条件**：李老师已发起「调代课」流程并正确关联双方课程快照；王老师为流程审批人。
- **主流程**：
  1. 王老师收到钉钉待办，打开审批单，核对类型（代课）、己方课程（李老师的 2 节）、对方（赵老师）；
  2. 点击同意；
  3. 系统自动将己方 2 条快照的授课教师改为赵老师，并在快照描述中追加「->赵老师」换课标记；
  4. 审批完成，双方收到通知；被代课程即刻在双方课表上生效。
- **异常流程**：
  - A1：类型为「调课」但双方所选课程数不对等 → 提交阶段即被拦截（提示"您调课必须使得双方所选课程数对等！"），不会进入审批；
  - A2：王老师驳回 → 快照不发生任何变更，流程终止。
- **后置条件**：快照反映新的授课关系；首页课表、巡课页面均显示变更后的教师；代课场景下赵老师课时 +2、李老师课时 −2（快照归属已变化，任何按教师统计的口径自动正确）。

#### 场景 S-03 配置选课课程库与选课管理（选课）

- **场景描述**：课后服务负责人张老师发布本学期的选修课：书法（30 分钟，3-4 年级，40 席）、机器人（60 分钟，5-6 年级，30 席）等。
- **前置条件**：张老师拥有「课程库-管理」权限。
- **主流程**：
  1. 在「课程库」录入每门课：课时（时长类型）、适合年级（多选）、名称、课程单位规模、席位、简介；
  2. 通知学生通过选课应用首页进入选课；
  3. 选课期间，张老师通过「选课-管理」视图实时查看报名数据，通过「班级学生选课统计」「选修课上课学生表」两张报表导出名单给任课教师。
- **异常流程**：
  - A1：某课程席位设置过小导致很快满员 → 学生端实时显示剩余席位 0，学生改选其他课程，无需管理员介入；
  - A2：课程信息填错 → 管理员直接编辑课程库记录，学生端 1 秒内（轮询刷新）生效。
- **后置条件**：学生选课记录归档；按课程的学生名单可用于上课点名。

#### 场景 S-04 学期末归档（智能课表）

- **场景描述**：学期结束，王老师确认本学期所有调代课已处理完毕，课表数据留档。
- **主流程**：快照数据本身即为学期归档（每条快照含日期、班级、科目、教师，天然构成历史记录）；王老师核对报表后，为下学期重新配置课表并孵化新快照。
- **后置条件**：历史学期快照保留，可按日期范围回溯任意一天的课表实况。

### 3.2 任课教师

#### 场景 S-05 查看个人课表（智能课表）

- **场景描述**：英语刘老师想看看自己本周在哪些班有课、下周是否有变化。
- **前置条件**：刘老师在「可索引教师」池中；快照已孵化。
- **主流程**：
  1. 打开智能课表首页，系统显示校区下拉（自动选中首个校区）；
  2. 刘老师在「教师」下拉中选择自己（教师维度查询会清空班级条件，二者互斥）；
  3. 页面渲染当周课表网格：行为节次（按优先级排序），列为周一至周日，格内显示授课教师/科目信息；
  4. 点击「上一周/下一周」切换周次，查询范围整体平移 7 天。
- **异常流程**：
  - A1：1 秒内连续切换班级/教师 → 触发互斥锁，后一次切换被忽略，防止查询条件交叉污染；
  - A2：某格子为空 → 该日该节次无课（未排或漏孵化）。
- **后置条件**：无（只读）。

#### 场景 S-06 发起代课（智能课表）

- **场景描述**：刘老师明日下午第 6 节临时有会，请同组的陈老师代课。
- **前置条件**：双方课程均已在快照中。
- **主流程**：
  1. 打开「调代课」流程表单，类型选择「代课」，页面即时显示提示："申请者（您）将会减少课时，被申请者（对方）将会增加课时。"；
  2. 「自己」字段只读回显本人；选择己方校区、己方日期，通过关联表单选择自己的那节课程快照；
  3. 选择对方（陈老师）、对方校区、对方日期、对方课程（代课场景下对方课程用于通知告知，审批通过后仅己方快照换教师）；
  4. 提交，进入审批；
  5. 审批通过后，该节快照教师变为陈老师并追加换课标记。
- **异常流程**：
  - A1：选错课程 → 审批人可驳回，快照不变；
  - A2：误选「调课」类型但只选了自己一方的课程 → 提交前被"课程数对等"规则拦截。
- **后置条件**：课表实况更新；双方钉钉收到结果通知。

#### 场景 S-07 发起调课（智能课表）

- **场景描述**：刘老师想把自己周三第 3 节的英语课与陈老师周四第 5 节的英语课对调。
- **主流程**：同 S-06，但类型为「调课」，且必须同时选择己方课程与对方课程且数量对等；审批通过后系统**互换**两条快照的授课教师（己方快照→陈老师，对方快照→刘老师），双方描述均追加「->对方」标记。
- **后置条件**：两节课的教师归属互换，双方课时总量不变。

### 3.3 班主任与体育教师

#### 场景 S-08 体育课双角色考勤（体育考勤）

- **场景描述**：周三第 3 节是 702 班的体育课。学生小明上午向班主任周老师请了病假；体育老师郑老师照常点名。
- **前置条件**：体育考勤「班级」表中已配置 702 班：班主任=周老师、缺省体育老师=郑老师、学生名单含小明；「课程」流程已配置审批。
- **主流程（班主任侧）**：
  1. 周老师发起「课程」流程，发起者身份选择「班主任」；
  2. 系统按其 userId 反查班级表，自动锁定班级=702 班、自动填充班主任与体育老师（字段禁用防篡改）；
  3. 学生名单自动带出；周老师在小明行的「请假」列选择"是"，其余学生选择"否"；「到勤」列与「竞合结果」列此时隐藏；
  4. 提交流程。
- **主流程（体育老师侧）**：
  1. 郑老师发起同一流程，发起者身份选择「体育老师」；
  2. 系统反查其名下所有班级供选择（一个体育老师带多班），选定 702 班后班主任自动带出；「请假」列只读、「到勤」列可编辑；
  3. 点名：小明「到勤」=否（没来），其余学生到勤=是；
  4. 每个学生的「竞合结果」实时计算：请假=否 且 到勤=否 → "异常"，否则 → "正常"。小明请假=是、到勤=否 → "正常"（请假且未到，符合预期）；
  5. 提交流程，走审批归档。
- **异常流程**：
  - A1：**静默缺勤**：某学生未请假（请假=否）也未到（到勤=否）→ 竞合结果="异常"，进入异常检测报表；
  - A2：**请假冲突**：学生请了假却出现在操场（请假=是且到勤=是）→ 同样计为正常（人在即安全），但班主任可核对假条真伪；
  - A3：班级表未配置该班主任/体育老师 → 反查为空，无法自动带出班级，需管理员先补配置。
- **后置条件**：每节课每个学生一条考勤结论；「异常检测」报表聚合展示异常记录。

### 3.5 巡课管理员

#### 4.1.4 关键业务流程

**流程 B-1-01 课表孵化（F-1-03）**

```
管理员录入课表（班级 × 学期 × 节次 × 7天科目教师）
        │
        ▼ 输入口令，点击生成
遍历每条课表 ──► 取学期范围 [起始日, 结束日]
        │
        ▼ 从起始日逐日推进（含周末）
取当日星期 → 定位该天的 科目/教师 列
        │
        ▼ 遍历每个节次行
科目与教师均非空？ ──否──► 跳过（空格不产快照）
        │是
        ▼
组装快照：[Configuration]=SystemProtected、描述行、
校区、节次、班级、日期、科目、授课教师(userId)
        │
        ▼ 并发写入（失败自动重试），进度实时回显
全部完成 → toast「已完成」
```

**流程 B-1-02 调代课（F-1-09 / F-1-10）**

```
教师发起流程
  ├─ 选类型：调课（双方课时不变）/ 代课（己减对方增）
  ├─ 己方：校区 + 日期 + 课程快照（关联表单，多选）
  ├─ 对方：教师 + 校区 + 日期 + 课程快照
  └─ 提交前校验：类型=调课 时，双方课程数量必须相等
        │
        ▼ 进入审批（钉钉待办）
审批人核对 → 同意 / 驳回
        │同意
        ▼ 审批通过钩子（仅 agree 触发）
代课：己方每条快照 → 授课教师=对方，描述追加 "->对方"
调课：在代课逻辑之上，对方每条快照 → 授课教师=己方，描述追加 "->己方"
        │
        ▼
快照即刻反映新授课关系（首页/巡课同步可见）
```

> 规则说明：调代课直接改写快照而非另存变更单，因此"快照=实况"这一不变式始终成立——这是智能课表与省心课表（实时计算模型）的本质差异（见 4.2）。

**流程 B-1-03 巡课（F-1-11）**

```

### 4.2 子系统二：省心课表（APP_WRJWKV4Q4LACDC0DYIJX，暂不启用）

#### 4.2.4 关键业务流程

**流程 B-2-01 实时计算引擎（课表叠加，F-2-04/F-2-05）**

```
加载基准周课表 rows（班级或教师维度）
        │

逐条展开效果 effects[节次|周内偏移]：
  代课 → (班级, 日期, 节次) ← 新教师，标记「代」
  调课 → (班级, 日期, 节次) ← 对调教师，标记「调」

输出 = 基准课表深拷贝 + 覆盖命中格的教师与标记

**流程 B-2-02 调代状态机（F-2-09）**

```
发起（状态=待确认，记录发起人/发起时间）
   │
   ├─ 原教师（代课）/对调教师（调课）确认
   │     └─ 先唯一性校验：所涉课格（调课含对方课格）
   │        检索同班同状态的已确认记录，同日期同节次即冲突
   │        冲突 → 拒绝确认并提示占用详情
   │        通过 → 状态=已确认（课表视图即刻体现）
   ├─ 确认人拒绝 → 状态=已拒绝
   └─ 发起人撤销（已拒绝/已撤销态除外）→ 状态=已撤销

按钮可见性规则：
  确认按钮：状态=待确认 且 当前用户=原教师（代课）或 对调教师（调课）
  撤销按钮：当前用户=发起人 且 状态非 已拒绝/已撤销
```

### 4.4 子系统四：体育考勤（APP_E2FPUS6TDIU0MWDY40W6）

#### 4.4.1 功能概述

体育考勤应用解决体育课"室外场景、单方点名、信息孤岛"的考勤失真问题。核心机制是**双角色竞合**：

- **班主任**发起考勤流程时，为已请假学生标注「请假」；
- **体育老师**发起（或同流程并发）时，为实际到勤学生标注「到勤」；
- 系统按规则自动比对两者得出每个学生的**竞合结果**（正常/异常），异常（未请假且未到勤）自动进入异常检测报表，当天即可见。

两人各自独立填报互不可见（班主任看不到到勤列、体育老师看不到请假列），从机制上杜绝了"抄对方答案"。

| 页面 | 类型 | 说明 |

| 课程 | process | 体育课考勤流程（双角色入口 + 竞合计算） |
| 班级 | receipt | 班级配置：班级-班主任-缺省体育老师-学生名单 |
| 异常检测 | report | 竞合结果为异常的考勤记录聚合报表 |

| 学生 | TableField | 子表：姓名（只读）+ 请假（RadioField）+ 到勤（RadioField，HIDDEN） |
| 竞合结果 | TextField | 子表列，公式实时计算：正常 / 异常，DISABLED |

> 竞合规则（handleCalcResultByMultiState）：`竞合结果 = !(请假 == 否 && 到勤 == 否) ? "正常" : "异常"`，即：**未请假且未到勤 → 异常**；其余（请假未到、请假到、未请假到）均正常。注：请假=是 且 到勤=是（请了假却来了）同样计"正常"，交由班主任事后核对。

#### 4.4.4 关键业务流程

**流程 B-4-01 双角色竞合考勤（F-4-02 ~ F-4-06）**

```
[班主任侧]                          [体育老师侧]
发起流程，身份=班主任                发起流程，身份=体育老师
│                                   │
▼ 按 userId 反查班级表命中其班        ▼ 列出其名下全部班级
班级自动锁定；班主任/体育老师/学生名单带出  │ 选班 → 班主任带出
请假列=可编辑；到勤列=隐藏            请假列=只读；到勤列=可编辑
学生小明：请假=是                    ▼ 点名
│                                  学生小明：到勤=否
└──────┬────────────────────────────┘
       ▼ 行内实时计算（双列均在场后）
请假=否 且 到勤=否  → 竞合结果=异常（静默缺勤）
其余组合           → 竞合结果=正常
       │
       ▼ 各自提交流程（可先后、可并发，不互相阻塞）
       ▼
异常记录自动进入「异常检测」报表 → 当天可见，德育/教务跟进
```

> 设计意图：异常 = "两头都没人管"的学生。班主任说请了假、体育老师说没来（正常，有交代）；班主任没说请假、体育老师说来了（正常，人在）；唯独"没请假也没来"被机器捕获——这正是单方点名永远发现不了的安全盲区。

### 6.3 数据流向

1. **课表数据流（智能课表）**：基础表（校区/班级/节次/科目/教师）→ 课表（周定义）→ 孵化 → 快照（物化）→ 查询/巡课/调代改写。快照为**单向物化**：改写只发生在调代课审批钩子；重孵化前必须先清场（F-1-04），不存在增量同步。
2. **课表数据流（省心课表）**：课表（周定义）→ 展示层实时叠加已确认调代记录 → 视图输出。**无物化层**，调代撤销即恢复原貌。
3. **选课数据流**：课程库（权威）→ 选课记录（学生行为）→ 反算剩余席位 → 报表出口。选课记录只增不删改（管理端可管理）。
4. **考勤数据流**：班级表（花名册权威）→ 双角色填报（互不可见）→ 竞合公式 → 异常报表。流程实例即考勤事实。
5. **教研数据流**：预约（触发源）→ 任务（跟踪载体）→ 听课/研讨记录（成果载体）→ 报表。流水号贯通全链。

## 8. 约束与假设

### 8.1 技术约束

1. **平台约束**：所有应用运行于宜搭低代码平台，自定义页面受 React16 类组件模型限制（export function 生命周期、_customState 状态、箭头事件、无计算属性名、异步 API 必须 .catch）。
2. **数据接口约束**：页面 JS 直接调用宜搭内部数据接口（带 _csrf_token），属平台私有能力；平台升级可能导致接口变化，需在升级后回归验证。
3. **前端计算约束**：快照孵化、选课校验、竞合计算、调代叠加、状态机确认等关键逻辑均在前端执行，依赖浏览器环境；长任务（孵化/清理）期间需保持页面打开。
4. **数据一致性约束**：智能课表快照为物化模型，基础数据变更不自动同步快照；学期中途调整基础数据（如班级更名）需评估重孵化成本。
5. **并发约束**：选课"最后一席"为前端轮询 + 点击时校验，极端并发下存在超员窗口；调代课审批改写快照为串行任务队列，无锁机制。
6. **省心课表暂不启用**：其表单结构与智能课表同构，数据可迁移；启用前需完成口令、花名册（userId）与 Excel 导入的回归验证。

### 8.2 业务假设

1. 一个班级在一个学期内只有一条周课表定义（含完整学期范围）；
2. 教师以钉钉账号为准一身份；省心课表要求教师花名册含 userId 方可发起调代；
3. 调代课由当事人自主发起，教导处仅审批把关，不代录（纸质代办由管理员代录除外）；
4. 学生不绑定钉钉账号：选课以姓名+年级+班级标识，重名/重复提交由管理端报表核对；
5. 体育课按"班级"组织考勤，每班每节课一条流程实例；体育老师带多班时按班逐条发起；
6. 听评课预约未上传附件视为常规听课（需派发任务），上传附件视为资料审阅型（不派发）；
7. 快照/课表数据量按单学期数万条计，历史学期数据只读归档；
8. 使用人员具备钉钉使用基础；管理员具备 Excel 操作能力（省心课表 Excel 导入）。

## 附录 A：已知问题与后续迭代建议

1. **选课并发超员**：前端校验无法防御"最后一席"并发竞争，建议在服务端（宜搭集成自动化/后端扩展）补充原子扣减；
2. **快照物化与基础数据解耦**：学期中改基础数据（班级更名、教师离职）不联动快照，建议提供"重孵化影响评估"工具或增量修正；
3. **学生身份弱绑定**：选课以文本标识学生，建议后续对接钉钉家校通讯录实现学生实名；
4. **省心课表启用条件**：启用前需完成花名册 userId 完整性与 Excel 导入回归；
5. **考勤异常跟进闭环**：异常报表目前仅呈现，建议增加"核查-处置-回填"的跟进流程；
6. **听评课任务逾期提醒**：任务完成后无自动提醒，建议增加临近课日提醒与完成率周报推送；
7. **CDN 依赖治理**：业务代码与第三方库依赖 CDN（cdn.ahkdxx.cn），建议建立缓存与降级方案，避免 CDN 故障导致应用不可用。
