## 1. 文档概述

### 1.1 编写目的

本文档定义"安徽钉钉学校"校园用餐管理领域的产品需求，覆盖**放心餐**与**用餐管理**两个宜搭应用的全部功能范围。

文档目的包括：

- 向项目干系人（校方管理层、食堂运营方、教育主管部门、开发团队、测试团队）清晰传达用餐管理系统"解决什么问题、解决谁的问题"；
- 作为设计、开发、测试与验收的基线依据，明确每个功能"做到什么程度算完成"；
- 沉淀从现有宜搭应用页面逻辑中逆向提炼的业务规则，防止后续迭代发生需求漂移；
- 为"放心餐"食品安全透明化这一核心价值主张提供可度量、可验收的需求表述。

### 1.2 项目背景与范围

**在范围内的能力：**

| 子系统 | 应用名称 | 定位 |
|--------|----------|------|
| 食品安全透明化子系统 | 放心餐 | 面向管理层与家长侧的餐标公示、带量带价菜谱发布、多校总览 |
| 日常用餐服务子系统 | 用餐管理 | 面向师生的用餐注册、点餐、每日用餐状态记录与审查报表 |

**不在本期范围内（Non-Goals）：**

- 食堂采购、库存、供应链管理系统（食材采购台账不在本系统内闭环）；
- 餐费收缴、财务结算与对账（本系统不处理资金流）；
- 明厨亮灶视频监控流媒体接入（后续可规划，本期不做）；
- 家长端独立 App / 小程序（本期依托钉钉生态触达）；
- 营养分析、膳食热量计算等专业营养学功能。

## 2. 产品愿景与定位

### 2.1 背景与问题陈述

校园用餐是家长最敏感、社会关注度最高的校园议题之一。当前领域存在三类典型痛点：

**痛点一：食品安全信息不对称，家长信任成本高**

家长无法了解孩子在校"吃了什么、吃了多少、花多少钱"。菜谱不公开、餐标不透明，一旦发生食品安全舆情，学校陷入自证困境。教育主管部门对"集中用餐信息公开"的监管要求日趋严格，学校需要一套低成本、可持续、留痕可追溯的公示机制。

**痛点二：多校区管理缺乏抓手，管理层看不见全局**

集团校、学区制办学模式下，管理层需要掌握各校区的餐标执行与菜谱公示情况，但传统做法依赖微信群逐校收图、人工核对，信息分散、难以对比、无法沉淀。"哪所学校这周菜谱公示了、哪所学校周五的餐标还没报"这类问题，管理层只能靠人肉催办。

**痛点三：日常用餐管理靠纸质登记，数据无法闭环**

师生用餐注册、点餐、核销依赖纸质台账或口头报备，导致：食堂备餐量凭经验估计，浪费与不足并存；请假、缺勤与用餐状态脱节；学期末统计就餐情况需要人工翻账，用餐状态缺乏审查依据。

**产品回应：** 用餐管理系统以"两个应用、一个闭环"的方式回应上述痛点——放心餐解决"让管理层看得见、让家长信得过"的问题；用餐管理解决"让师生用得顺、让食堂管得准"的问题。

### 2.2 产品定位

一句话定位：**让每一顿饭的"标准、内容、状态"全程透明、全程留痕的校园用餐数字化平台**。

| 维度 | 定位说明 |
|------|----------|
| 业务域 | 校园后勤服务——用餐管理 |
| 平台形态 | 钉钉宜搭低代码应用，嵌入钉钉工作台，免安装、免培训 |
| 组织形态 | 支持单一学校与多校区（集团校）两种形态，多校为一级数据维度 |
| 时间模型 | 学年 → 学期 → 周次 → 周内日次 → 日期的五级校园时间坐标 |
| 价值取向 | 透明优先（公示、留痕、可追溯）；效率其次（注册、点餐、核销线上化） |

### 2.3 放心餐：食品安全透明化价值主张（重点）

放心餐是本系统的价值旗帜，其核心主张是：**把"孩子在学校的每一顿饭"变成学校主动公开、家长随手可查、管理层全局可见的透明信息**。

**价值一：带量带价，回应"吃得值不值"**

传统校园菜谱公示只写菜名（如"红烧肉、炒青菜"），家长无从判断分量与成本。放心餐要求发布**带量带价菜谱**：每道菜标注食材用量（如"猪肉 50g、土豆 100g"）与价格构成。这一做法同时回应两类关切：

- 食品安全关切：食材明细公开，倒逼食堂规范采购与加工，也让过敏体质学生的家长有据可查；
- 费用合理性关切：餐费花在哪里一目了然，消除"餐费去向不明"的家校矛盾。

**价值二：每日餐标，回应"标准有没有执行"**

餐标是学校对每餐质量与价格的承诺。放心餐要求按"学校 × 日期"逐日上传餐标凭证图片，将"执行承诺"转化为可核查的留痕记录。管理层在总览看板中一眼即可发现"哪所学校、哪一天未公示"，把事后追责变为过程督导。

**价值三：多校总览，回应"管理有没有抓手"**

全局总览以矩阵方式（行=学校，列=周菜谱+周一至周日餐标）呈现全域公示情况，并自动将周次记录换算为具体日期标注在表头上。对教育主管部门与集团管理层而言，这是一块"不打招呼、直插现场"的电子巡查屏。

**价值四：留痕即证据，回应"舆情来了怎么办"**

所有餐标与菜谱记录均带有提交人、提交时间等宜搭平台原生审计信息。一旦发生食品安全质疑，学校可快速调取对应周次、日期的公示凭证，形成完整的自证链条。

### 2.4 用餐管理：日常服务价值主张

用餐管理面向每日高频使用场景，主张是：**注册一次、点餐一步、状态可查、报表可审**。

- 用餐注册按"学年学期"粒度一次办理，编码自动生成（如 2025A），避免重复登记；
- 点餐交互极简，用餐人与日期自动带出，师生（或值班教师代学生）一步完成，适配餐厅一体机等公共终端场景；
- 每日用餐状态以勾选核销方式记录，审查报表支撑管理者比对"应餐人数 vs 实餐人数"；
- 首页聚合"待办、我创建的、抄送我的"三类钉钉任务，让用餐相关审批与提醒有统一入口。

### 3.2 食堂管理员场景

**角色描述：** 各校食堂的日常运营负责人，工作节奏紧跟供餐日历，信息化能力一般，需要"填得少、错不了"的录入体验。

**场景 S1：每周发布带量带价菜谱（周五发布下周菜谱）**

- 前置条件：食堂已确定下周菜谱，并完成食材用量与价格的核算；管理员已登录钉钉。
- 触发：每周五下午，食堂完成下周菜谱定稿。
- 过程：
  1. 管理员进入放心餐"每周带量带价菜谱"表单；
  2. 选择本校（多校共用场景下必选，单校场景下为唯一选项）；
  3. "周次"字段由系统自动带出，格式为"YYYY-YYYY学年第X学期第N周"，无需手工填写，避免写错周次；
  4. 管理员将制作好的带量带价菜谱图片（含菜名、食材用量、单价）上传，支持多张图片（如分页拍摄）；
  5. 提交保存。
- 后置条件：该"学校×周次"的菜谱记录生效，可在下周的全局总览中展示，供家长与管理层查阅。
- 异常路径：菜谱图片不清晰或漏项——允许同一学校同一周次重新提交覆盖（以最新记录为准，具体以宜搭数据权限配置为准）。

**场景 S2：每日上传餐标凭证（每日开餐前）**

- 前置条件：当日餐食已按标准备好，餐标公示牌已在餐厅摆放并拍照。
- 过程：
  1. 管理员进入放心餐"每日餐标"表单；
  2. 选择学校；
  3. "周次"与"周内日次"均由系统自动带出（如"第3周"+"周三"），管理员无需关心今天是学年第几周；
  4. 上传当日餐标图片（可多张：价格公示牌、菜品实拍）；
  5. 提交保存。
- 后置条件：当日餐标公示留痕完成，总览看板中该校当日格子显示实图。
- 业务规则：每个"学校×周内日次"对应一条餐标记录；未上传的日期在总览中显示占位图，即视为"未公示"，供管理层识别。

### 3.3 学校管理员场景

**角色描述：** 学校办公室或后勤部门负责人，负责本校基础数据维护与用餐数据的内部治理。

**场景 S3：维护学校基础信息**

- 前置条件：新学校接入系统，或学校名称/归属发生变更。
- 过程：
  1. 管理员进入放心餐"学校"表单，录入学校名称；
  2. 页面加载时系统自动触发一次外部数据同步（调用配置的远程数据源），保证学校主数据与上级平台保持一致；
  3. 保存后，该校即可在每日餐标、每周菜谱表单中被选择，并出现在全局总览的行中。
- 后置条件：学校主数据就绪，供本应用内各表单引用。

**场景 S8：用餐状态审查与纠偏（每日放学后 / 每周汇总）**

- 前置条件：当日师生已完成点餐与核销，用餐状态记录基本齐备。
- 过程：
  1. 管理员打开用餐管理的"用餐状态审查"报表；
  2. 按日期、用餐人、是否已用餐等维度筛选与统计；
  3. 比对异常：例如某学生已点餐但状态未核销（疑似漏刷/漏记），或某未注册人员出现用餐记录；
  4. 联系食堂或班主任核实后，修正对应"每日用餐状态"记录；
  5. 周度汇总实际就餐人次，作为食堂备餐量调整与费用公示的依据。
- 后置条件：用餐数据可信度达到审查要求，形成"记录—审查—纠偏"的闭环。

### 3.4 教师场景

**角色描述：** 一线教职工，信息化素养参差，核心诉求是"别占用教学时间"，所有操作应在 1 分钟内完成。

**场景 S5：学期初注册用餐（开学第一周）**

- 前置条件：新学期开学，教师需要在食堂用餐。
- 过程：
  1. 教师进入用餐管理"注册用餐"表单；
  2. 选择用餐人（员工组件选择本人）；系统自动将所选用户的钉钉 UID 回填到只读的 UID 字段，教师无感知、也无需理解 UID 概念；
  3. 选择学年（如"2025-2026"）与学期（如"第一学期"）；
  4. 系统按规则自动生成"学年学期编码"并回填只读字段：取学年起始 4 位数字 + 学期字母（第一学期=A，第二学期=B），例如"2025A"；教师只校验不录入；
  5. 提交完成注册。
- 后置条件：教师取得本学期用餐资格，后续点餐以此为基础。
- 业务规则：编码规则由系统保证唯一性与可读性，禁止手工修改，避免口径不一导致报表统计错误。

**场景 S6：每日点餐（上午课间 / 就餐前）**

- 前置条件：教师已完成当学期注册。
- 过程：
  1. 教师进入用餐管理"用餐"表单（可从首页或钉钉工作台直达）；
  2. 用餐人字段只读回显本人，日期字段只读回显当日，教师无需任何选择；
  3. 系统在后台记录 UNAME（姓名）与 UID 两个隐藏字段，用于后续报表定位到人；
  4. 教师确认提交，即完成点餐；
  5. 跳转"点餐成功"确认页，只读展示用餐人与日期，教师确认无误后离开。
- 后置条件：生成一条用餐记录，食堂可据此预估当日就餐人数。
- 场景变体：值班教师可代学生点餐——在允许代操作的权限配置下，用餐人字段选择被代点的学生后，系统同样回填其 UID，流程一致。

### 3.5 学生与家长场景

**角色描述：** 学生多为被服务方（低年级由教师协助操作）；家长是透明化价值的最终感知者，通过钉钉接收公示信息。

**场景 S9：家长查阅本周菜谱与餐标**

- 前置条件：学校已发布当周带量带价菜谱与当日餐标，且学校已配置对家长公开。
- 过程：
  1. 家长在钉钉班级群/家校通知中收到学校分享的菜谱公示链接（或经学校授权访问总览页面）；
  2. 查看本周菜谱图片：每道菜标注食材用量与价格；
  3. 如有食材过敏等特殊情况，家长据此提前与班主任沟通；
  4. 家长亦可逐日查看餐标公示图片，了解当日实际供应与价格标准。
- 后置条件：家长的知情权得到满足，家校信任增强；学校完成一次"主动公开"的履职留痕。
- 说明：家长访问范围与方式由学校按钉钉权限策略配置，本系统只保证数据"可被公开"，不强制公开方式。

**学生点餐场景：** 低年级学生不直接操作系统，由班主任或值班教师按名册代点（见 S6 变体）；高年级学生在教师组织下有序点餐。系统交互的极简设计（自动带出、一步提交）即为此场景服务。

### 3.6 监督与管理层场景

**场景 S4：集团管理层每周巡查各校公示（周一上午例会前）**

- 前置条件：各校已按流程发布上周/本周菜谱与餐标。
- 过程：
  1. 总校长打开放心餐"全局总览"页面；
  2. 页面自动汇总所有已发布菜谱的周次，按时间倒序排列（先按学年学期数值、再按周序号排序），并默认选中第二新的周次（通常是刚结束的上周），便于复盘；
  3. 看板自动把周次记录换算为具体日期标注在列头上（如"周一（2026/8/3）"），管理层无需心算日期；
  4. 逐行扫视：每所学校一行，第一列是该校本周带量带价菜谱，其后是周一至周日的餐标图片；显示占位图的格子即代表该校该日未公示；
  5. 切换顶部"周次"下拉框，可回看历史任意一周的公示全貌。
- 后置条件：管理层掌握各校公示完整率，对未公示学校点名督办；巡查过程本身也构成督导留痕。

**场景 S10：系统维护者进入开发者模式**

- 前置条件：维护者具备系统管理权限，且知晓隐藏入口规则。
- 过程：在用餐管理首页连续点击主图 5 次起，页面逐次提示"再点击 N 次进入开发者模式"；累计点击达到 8 次，自动跳转至开发者页面。
- 后置条件：维护者进入开发调试入口。
- 设计意图：该入口服务于开发与运维，不对普通用户暴露；普通用户点击无副作用（仅累计计数）。

#### 4.2.4 功能清单

**FR-A1 学校主数据维护**

- 功能目的：为多校公示体系提供稳定的行维度主数据。
- 功能说明：
  1. 支持新增学校记录，录入学校名称；
  2. 页面加载完成时，系统自动调用已配置的远程数据源（dp2，POST）触发一次外部同步，保持学校主数据与上级平台一致；
  3. 学校名称同时作为每日餐标、每周菜谱表单中"学校"下拉框的选项来源，以及全局总览矩阵的行标签。
- 业务规则：
  - BR-A1-1：学校名称在系统内应唯一，作为业务识别键；
  - BR-A1-2：学校被引用后（已有餐标/菜谱记录）原则上不做物理删除，仅停用，保证历史公示数据可追溯；
  - BR-A1-3：外部同步为"尽力而为"，同步失败不阻断本地学校信息的录入与使用。

**FR-A2 每日餐标公示**

- 功能目的：把每日餐标执行情况转化为可核查的图片留痕。
- 功能说明：
  1. 录入人选择学校后提交当日餐标图片；
  2. 周次由"学年（SchoolYear）→学期（Semester）→周（Week）"三级时间对象链式组合（compose）后自动注入"周次"字段并设为默认值，格式如"2025-2026学年第一学期第3周"；
  3. 周内日次由"周内日（WeekDay）"时间对象自动注入，取值"周一"～"周日"；
  4. 周次与周内日次字段均为只读，杜绝人工错填时间坐标。
- 业务规则：
  - BR-A2-1：一条餐标记录唯一对应一个"学校 × 周次 × 周内日次"组合；
  - BR-A2-2：同一组合重复提交时，总览展示以最新提交为准；
  - BR-A2-3：图片字段至少上传 1 张方可提交（公示凭证不可为空）；
  - BR-A2-4：时间坐标以提交时刻所在自然周为准（由系统时间对象推导，非人工选择）。

**FR-A3 每周带量带价菜谱发布**

- 功能目的：以周为单位发布含食材用量与价格的菜谱，实现食品安全与费用透明双公示。
- 功能说明：
  1. 录入人选择学校；
  2. 周次同样由"学年→学期→周"链式自动注入，只读；
  3. 上传带量带价菜谱图片（多张），提交发布。
- 内容要求（产品层面对菜谱图片的约定）：
  - 应包含周一至周五（供餐日）每日菜品清单；
  - 每道菜应标注主要食材用量（带量）与价格（带价）；
  - 图片应清晰可读，分辨率满足放大查看需求。
- 业务规则：
  - BR-A3-1：一条菜谱记录唯一对应一个"学校 × 周次"组合；
  - BR-A3-2：菜谱发布时间应不晚于供餐周的周一（管理要求，系统不做强校验）；
  - BR-A3-3：菜谱记录一经发布即进入全局总览与历史归档，修改以重新提交覆盖方式进行。

**FR-A4 全局总览看板**

- 功能目的：为管理层提供"学校 × 日期"二维公示矩阵，一屏掌握全域公示完整度。
- 功能说明：
  1. **周次选项构建**：页面加载时读取全部菜谱记录，对周次字段去重后按时间语义倒序排序——解析周次文本中的学年与周序号，换算为"学年4位 + 周2位"的数值键（如第5周记为 YYYY05）比较，数值大者在前；排序结果填入"周次"下拉框；
  2. **默认选中策略**：默认选中次新周次（第二项），若只有一周数据则选中唯一项。设计意图是便于管理层复盘刚结束的上一周，而非只看尚在进行的本周；
  3. **矩阵数据加载**：切换周次时并行读取三组数据——学校列表、该周菜谱记录、该周每日餐标记录；
  4. **列头日期换算**：从该周餐标记录中定位"周一"记录的创建时间，推算周一至周日的具体日期，将表格列头动态改写为"周一（2026/8/3）"样式；若该周无周一记录（或记录缺失），列头退回为无日期的"周一～周日"纯文字，保证看板可用性不因数据缺失而崩溃；
  5. **矩阵填充**：以学校为行，每行第一列为该校本周菜谱图片（取菜谱记录的图片下载地址），其后依次为周一～周日的餐标图片；未匹配到图片的单元格填充固定占位图；
  6. **加载态**：数据请求期间表格显示 loading 态，避免空数据闪烁。
- 业务规则：
  - BR-A4-1：周次排序必须正确处理跨学年比较（不同学年的周次按数值键统一排序）；
  - BR-A4-2：日期换算只依赖"周一"餐标记录的创建时间，其余日序按 +1 天递推；
  - BR-A4-3：占位图仅表示"未公示/无图"，不代表"当日未供餐"（假期等情形不做区分）；
  - BR-A4-4：看板为只读视图，不提供任何写操作。
#### 4.2.5 业务流程

**流程 P1：每周菜谱发布流程**

```
食堂定稿下周菜谱
      │
      ▼
食堂管理员核算食材用量与价格，制作带量带价菜谱图
      │
      ▼
打开「每周带量带价菜谱」表单 → 选择学校
      │
      ▼
系统自动注入周次（只读）
      │
      ▼
上传菜谱图片（≥1张）→ 提交
      │
      ▼
记录入库（学校×周次唯一对应）
      │
      ▼
周一供餐周开始 → 全局总览该周矩阵呈现菜谱列
      │
      ▼
家长/管理层查阅（透明化价值兑现）
```

**流程 P2：每日餐标公示流程**

```
当日备餐完成、餐标公示牌就位
      │
      ▼
食堂管理员拍照（价格牌+菜品）
      │
      ▼
打开「每日餐标」表单 → 选择学校
      │
      ▼
系统自动注入周次+周内日次（均只读）
      │
      ▼
上传图片 → 提交留痕
      │
      ▼
全局总览当日格子由占位图变为实图
      │
      ▼
管理层巡查发现缺图 → 督办补报（闭环）
```

**流程 P3：管理层周度巡查流程**

```
打开「全局总览」
      │
      ▼
系统自动汇总周次 → 倒序排列 → 默认选中次新周
      │
      ▼
并行拉取：学校列表 + 该周菜谱 + 该周餐标
      │
      ▼
列头自动换算具体日期（以周一记录推算）
      │
      ▼
矩阵呈现：行=学校，列=菜谱+周一至周日
      │
      ▼
识别占位图（未公示）→ 切换周次可回看历史
      │
      ▼
形成巡查结论 → 督办/表扬
```

| 家长（经授权） | — | — | — | 查看（按学校授权范围） |

权限实施说明：

- 基于宜搭平台的"数据权限 + 页面权限"机制实现：表单提交权限控制"谁能写"，数据行权限控制"能看哪个学校的数据"；
- 多校场景下，食堂管理员的数据范围应按其所属学校过滤；管理层账号不设学校过滤；

- 所有提交记录保留宜搭原生审计字段（创建人、创建时间、修改人、修改时间），支撑留痕追溯。

#### 4.3.4 功能清单

**FR-B1 应用首页与任务聚合**

- 功能目的：为师生提供统一的应用入口，聚合与用餐相关的钉钉任务流，降低"信息找不着"的成本。
- 功能说明：
  1. 页面配置三类任务数据源：待办任务（getTodoTasks）、我创建的（getMySubmmit）、抄送我的（getNotifyMeTasks），首页聚合展示；
  2. 首页主图承担品牌与导航职能；
  3. 隐藏开发者入口：页面维护一个点击计数器（值数据源 clickCounter），主图每次点击计数加一；累计 5 次起，每次点击提示"再点击 N 次进入开发者模式"；累计达到 8 次，路由跳转至开发者页面；
  4. 计数为页面级状态，刷新或重进页面后归零，避免误触累积。
- 业务规则：
  - BR-B1-1：5 次以下的点击不产生任何提示与跳转，普通用户无感知；
  - BR-B1-2：开发者入口仅作为运维便利通道，不承载任何业务数据的写操作；
  - BR-B1-3：任务聚合展示遵循钉钉任务数据源的既有权限，用户只能看到属于自己的任务。

**FR-B2 注册用餐**

- 功能目的：以学期为粒度一次性登记用餐资格，并通过自动编码保证统计口径统一。
- 功能说明：
  1. 用户通过员工组件选择用餐人；页面加载时与每次切换用餐人时，系统均将所选用户的 userId 回填至只读 UID 字段（加载回填存在短暂异步延迟，属正常现象）；
  2. 用户选择学年与学期（单选）；
  3. 学年或学期任一变化时，系统自动重算学年学期编码：取学年文本前 4 位数字，拼接学期字母（"第一学期"→A，其余→B），写回只读编码字段；两项未选全时不计算、不清空等待；
  4. 提交后完成注册。
- 业务规则：
  - BR-B2-1：UID 与编码字段只读，用户不可手工修改；
  - BR-B2-2：编码生成规则全局唯一且稳定——同一"学年+学期"输入永远得到同一编码（如"2025-2026学年"+"第一学期"→"2025A"）；
  - BR-B2-3：同一用餐人在同一学年学期内原则上仅注册一次，重复注册视为更新；
  - BR-B2-4：注册是点餐的前置条件（管理约束）：未注册人员的点餐记录在审查环节应被识别为异常。

**FR-B3 点餐（用餐）**

- 功能目的：以最低操作成本完成每日点餐，适配公共终端与代点场景。
- 功能说明：
  1. 用餐人字段只读回显（默认本人；代点场景由前置流程选定对象）；
  2. 日期字段只读回显当日；
  3. 用餐人变化时，系统联动写入两个隐藏字段：UNAME（用户姓名）与 UID（用户 userId），用户全程不可见；
  4. 提交即完成点餐，进入"点餐成功"确认页。
- 业务规则：
  - BR-B3-1：点餐记录的业务键为"用餐人(UID) × 日期"，同一人同一天重复点餐视为同一记录（幂等语义，避免重复计数）；
  - BR-B3-2：隐藏字段 UNAME/UID 是后续报表与审查的定位依据，必须随每次提交可靠落库；
  - BR-B3-3：日期以提交时系统日期为准，不支持补点历史日期（异常情况走审查纠偏流程）；
  - BR-B3-4：点餐动作不校验余额/餐费（本系统不处理资金流，见 1.2 范围声明）。

**FR-B4 点餐成功确认**

- 功能目的：给用户明确的操作闭环反馈，防止"点了没点不知道"。
- 功能说明：点餐提交后跳转本页面，只读展示用餐人与日期两个关键字段（数据经页面参数传递），用户确认后离开。
- 业务规则：
  - BR-B4-1：确认页为纯展示页，不提供修改与撤销入口；如需撤销走管理员纠偏通道；
  - BR-B4-2：展示内容必须与刚落库的用餐记录一致。

**FR-B5 每日用餐状态核销**

- 功能目的：记录"实际是否用餐"，把点餐意向转化为核销事实，支撑备餐精度与费用审查。
- 功能说明：
  1. 食堂核销员（或值班教师）选择用餐人（员工组件），录入/联动 UID；
  2. 选择日期（默认当日）；
  3. 勾选"已用餐"表示该用户当日实际用餐；未勾选表示未用餐；
  4. 提交形成状态记录。
- 业务规则：
  - BR-B5-1：状态记录的业务键为"用餐人(UID) × 日期"；
  - BR-B5-2：核销动作通常发生在就餐现场（打卡/点名后），应支持批量场景下的快速连续录入；
  - BR-B5-3："已用餐"勾选状态允许在审查环节修正（如误勾），修正留痕。

**FR-B6 用餐状态审查报表**

- 功能目的：为管理者提供"应餐—点餐—实餐"三层数据的比对与统计能力，发现并纠正异常。
- 功能说明：
  1. 报表基于每日用餐状态数据构建，支持按日期、用餐人、是否已用餐等维度筛选；
  2. 支持统计汇总：指定日期范围内的已用餐人次、未用餐人次；
  3. 管理者结合注册用餐数据与用餐记录数据，人工比对异常（审查页为报表型页面，复杂比对逻辑由审查流程承载）。
- 业务规则：
  - BR-B6-1：报表数据随源数据实时更新，不提供缓存快照；
  - BR-B6-2：报表仅面向管理角色开放，师生个人不可见全量数据；
  - BR-B6-3：审查发现的异常须回到对应表单（状态/注册/点餐）修正，报表本身不提供数据修改。

**FR-B7 开发者模式隐藏入口**

- 功能目的：为开发维护人员保留便捷调试通道，同时不干扰普通用户。
- 功能说明与规则：见 FR-B1 及其 BR-B1-1/2/3；补充规则：
  - BR-B7-1：入口行为（5 次起提示、8 次跳转）为产品级约定，改版时不得随意变更阈值，除非同步更新运维文档；
  - BR-B7-2：开发者页面的访问仍受宜搭页面权限约束，隐藏入口不等于权限绕过。

#### 4.3.5 业务流程

**流程 P4：学期用餐注册流程**

```
开学通知（学校管理员发布注册要求）
      │
      ▼
师生进入「注册用餐」表单
      │
      ▼
选择用餐人（员工组件）──联动──► UID 自动回填（只读）
      │
      ▼
选择学年 + 学期
      │
      ▼
系统生成学年学期编码（如 2025A，只读）
      │
      ▼
提交 → 注册生效
      │
      ▼
学校管理员通过报表核对注册率 → 催办未注册人员（闭环）
```

**流程 P5：每日点餐与核销流程**

```
师生到达餐厅/值班教师组织点餐
      │
      ▼
进入「用餐」表单
      │
      ▼
用餐人（只读回显） + 日期（只读回显当日）
      │（后台联动写入 UNAME/UID 隐藏字段）
      ▼
一步提交 → 生成用餐记录
      │
      ▼
跳转「点餐成功」确认页 → 用户离开
      │
      ▼
就餐现场：食堂核销员在「每日用餐状态」中
选择用餐人 + 日期 + 勾选「已用餐」→ 提交
      │
      ▼
学校管理员在「用餐状态审查」报表比对
应餐/点餐/实餐 → 异常纠偏（闭环）
```

关系要点：

- E1 学校 与 E2/E3 为一对多：一所学校拥有多条餐标记录与多份周菜谱；
- E2 每日餐标 的业务键为 学校 × 周次 × 周内日次；E3 每周菜谱 的业务键为 学校 × 周次；
- E4/E5/E6 以钉钉用户 UID 为贯穿主键，分别落在学期、日（点餐）、日（核销）三个粒度；
- 全局总览是 E1/E2/E3 的只读聚合视图；用餐状态审查报表是 E6（辅以 E4/E5 比对）的只读统计视图。

### 6.2 数据字典（关键字段）

**D1 时间坐标字段**

| 数据项 | 类型 | 格式/取值 | 生成方式 | 示例 |
|--------|------|-----------|----------|------|
| 周次 | 文本 | `{YYYY}-{YYYY}学年第{一/二}学期第{N}周` | 系统自动（学年→学期→周链式推导） | 2025-2026学年第一学期第3周 |
| 周内日次 | 文本 | 周一～周日 | 系统自动（WeekDay 时间对象） | 周三 |
| 学年学期编码 | 文本 | `{学年起始4位}{A/B}`，第一学期=A，第二学期=B | 系统自动（注册表单联动） | 2025A |
| 日期 | 日期 | 公历日期 | 系统回显当日 / 核销时选择 | 2026-08-05 |

> 说明：周次文本是全系统的"时间主数据"。全局总览通过正则解析其中的学年与周序号，换算为可比较的数值键完成排序；任何对周次文案格式的改动都会破坏排序与日期换算逻辑，属高危变更（见 9.2 回归测试要求）。

**D2 用户标识字段**

| 数据项 | 类型 | 来源 | 可见性策略 | 用途 |
|--------|------|------|------------|------|
| 用餐人（员工组件） | 钉钉用户对象 | 员工选择组件 | 可编辑/只读（按页面） | 用户交互入口 |
| UID | 文本 | 员工组件联动（user.value） | 只读或隐藏 | 业务键、报表定位 |
| UNAME | 文本 | 员工组件联动（user.label） | 隐藏 | 报表可读展示 |

**D3 图片附件字段**

| 数据项 | 类型 | 约束 | 用途 |
|--------|------|------|------|
| 餐标图片 | 图片数组（多张） | ≥1 张 | 每日餐标公示凭证 |
| 菜谱图片 | 图片数组（多张） | ≥1 张 | 带量带价菜谱公示 |
| 图片下载地址 | 文本（JSON 内 downloadUrl） | 宜搭附件存储 | 总览矩阵渲染取图 |

### 6.3 数据流向

**流向一：公示数据流（自下而上沉淀，自上而下监督）**

```
食堂现场（拍照）
   → 每日餐标 / 每周菜谱表单（结构化落库：学校+周次+图片）
   → 全局总览（聚合渲染：学校×日期矩阵）
   → 管理层巡查 / 家长查阅（透明化输出）
```

**流向二：用餐服务数据流（自下而上汇聚）**

```
钉钉组织架构（用户主数据）
   → 注册用餐（UID + 学年学期编码）
   → 用餐/点餐（UID × 日期）
   → 每日用餐状态（UID × 日期 × 已用餐）
   → 用餐状态审查报表（统计输出）
```

**流向三：主数据同步流（外部→本地）**

```
上级平台/外部系统
   → 学校表单 dp2 远程数据源（页面加载触发 POST 同步）
   → 学校实体本地存储
```

### 6.4 数据治理要求

| 编号 | 要求 | 说明 |
|------|------|------|
| DG-1 | 时间坐标只读 | 周次、周内日次、学年学期编码均为系统生成且只读，任何人不得通过数据管理侧随意改写格式 |
| DG-2 | 业务键唯一 | E2/E3/E5/E6 的业务键冲突处理遵循"最新提交为准"，但须保留历史记录（宜搭版本留痕） |
| DG-3 | 归档策略 | 学年结束后数据不删除；总览周次下拉按数值键排序天然支持跨年归档查阅 |
| DG-4 | 导出留档 | 建议每学期末导出菜谱/餐标公示清单与用餐统计报表，作为食品安全台账存档 |
| DG-5 | 图片治理 | 公示图片建议命名规范：{学校简称}-{周次}-{日期}-餐标/菜谱，便于线下归档 |

## 7. 集成需求

### 7.1 钉钉平台集成

| 编号 | 集成点 | 说明 |
|------|--------|------|
| INT-1 | 统一身份与免登 | 两应用均以钉钉工作台为入口，用户免登访问，无需独立账号体系 |
| INT-2 | 组织架构（员工组件） | 用餐管理三张表单的"用餐人"均使用 EmployeeField 员工组件，数据源为钉钉组织架构；用户选中即获得 UID（userId）与姓名，保证用餐人身份与钉钉实名体系一致 |
| INT-3 | 任务中心 | 用餐管理首页接入三类钉钉任务数据源：待办任务（getTodoTasks）、我创建的（getMySubmmit）、抄送我的（getNotifyMeTasks），用餐相关审批与提醒统一呈现 |
| INT-4 | 消息触达 | 依托钉钉群/工作通知能力，学校可将每周菜谱公示链接、注册催办、审查结果推送给对应人群（班主任群、家长群、食堂群） |
| INT-5 | 附件存储 | 餐标/菜谱图片使用宜搭附件存储，总览页面通过图片 JSON 中的 downloadUrl 渲染 |

### 7.2 外部系统集成

| 编号 | 集成点 | 说明 |
|------|--------|------|
| INT-6 | 学校主数据同步 | "学校"表单配置远程数据源 dp2（POST），页面加载时自动触发同步调用，用于与上级平台对齐学校主数据；调用参数与响应解析以集成配置为准，同步失败不得阻断本地功能 |
| INT-7 | 前端增强脚本 | 放心餐三个含自定义逻辑的页面在加载时引入统一的前端增强脚本（cdn.ahkdxx.cn 域），提供校园时间对象（学年/学期/周/周内日）与表单数据访问能力（QuickMap）；该脚本为公示类页面时间自动注入与总览聚合的运行时依赖 |

### 7.3 两应用间数据关联

放心餐与用餐管理是两个独立宜搭应用，不存在直接的系统级接口调用；其关联通过**共享业务语义**与**人工/消息流**衔接：

| 关联维度 | 说明 |
|----------|------|
| 组织维度 | 两应用同属"安徽钉钉学校"组织，共享钉钉用户体系（UID 一致），为未来数据打通保留基础 |
| 时间维度 | 共享学年-学期-周-日校园时间语义；放心餐的"周次"与用餐管理的"学年学期编码"均派生自同一时间模型 |
| 业务衔接 | 放心餐发布的菜谱/餐标是"供给承诺"，用餐管理产生的点餐/核销是"需求与执行"；管理层将两者对照即可评估"公示标准是否落地为实际供餐" |
| 触达衔接 | 学校管理员从用餐管理审查报表发现的供餐异常，可通过钉钉反馈至食堂，食堂在放心餐侧补报餐标公示，形成跨应用闭环 |
| 演进预留 | 若后续需要系统级打通（如按学校统计就餐率并叠加到总览看板），可通过宜搭开放 API 跨应用取数实现，当前版本不做 |

## 8. 约束与假设

### 8.1 约束

| 编号 | 约束 | 说明 |
|------|------|------|
| CON-1 | 平台约束 | 系统构建于钉钉宜搭低代码平台，功能形态受宜搭组件与能力边界约束；超出宜搭能力的需求（如复杂实时计算）需评估自建后端成本 |
| CON-2 | 时间模型约束 | 学年-学期-周时间坐标由增强脚本按中国大陆校历语义推导，不支持跨校历体系（如国际学校三学期制）开箱即用 |
| CON-3 | 菜谱表达约束 | 带量带价菜谱当前以图片形式承载（非结构化），系统无法对"量/价"做自动校验与统计；结构化菜谱属未来演进 |
| CON-4 | 资金边界约束 | 本系统不接入支付与财务结算，餐费收缴不在范围内 |
| CON-5 | 合规约束 | 信息公开范围须遵守未成年人信息保护相关要求；学生用餐数据的对外公开仅限菜谱/餐标等供餐信息，不含学生个体数据 |
| CON-6 | 组织约束 | 用餐注册与点餐依托钉钉组织架构，未入钉钉组织的人员（如临时访客用餐）不在系统覆盖范围 |
| CON-7 | 多校录入约束 | 食堂管理员代多校录入时依赖"学校"下拉选择，系统不做地理位置校验，录入准确性靠管理要求保证 |

### 8.2 假设

| 编号 | 假设 | 风险与对策 |
|------|------|------------|
| ASM-1 | 各校具备每日拍照并上传餐标凭证的执行能力（有智能手机与网络） | 若个别学校设备受限，管理层巡查会持续看到占位图；对策：纳入食堂考核并协助补齐设备 |
| ASM-2 | 学校按周历正常供餐，周内日次与供餐日一一对应 | 寒暑假、节假日的"未公示"在总览中同样显示为占位图；解读时以校历为准，系统不区分假期 |
| ASM-3 | 周次文案格式保持稳定（`YYYY-YYYY学年第X学期第N周`） | 格式漂移将破坏总览排序与日期换算（高危）；对策：周次字段只读 + 变更走需求评审 |
| ASM-4 | 第三方占位图外链长期可用 | 外链失效仅影响无图单元格的占位显示；对策：建立自有占位图资源并制定替换预案 |
| ASM-5 | 家长查阅依赖学校主动分享与授权 | 若学校不分享，透明化价值无法触达家长；对策：将"分享菜谱公示"纳入学校运营 SOP 与成功指标 |
| ASM-6 | 值班教师代学生点餐的组织方式可行 | 低年级场景依赖教师组织；对策：保留纸质兜底台账，事后补录 |
| ASM-7 | 钉钉与宜搭平台持续可用且能力兼容 | 平台升级可能影响自定义逻辑；对策：每次平台大版本升级后执行回归测试（见 9.2） |
| ASM-8 | 增强脚本 CDN 持续可用 | 脚本不可用导致放心餐自动注入失效；对策：CDN 监控告警 + 脚本版本冗余 |
