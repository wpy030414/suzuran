## 1. 文档概述

### 1.1 编写目的

本文档旨在完整、准确地定义"安徽钉钉学校"校园监控与信息平台的产品需求，作为该平台设计、开发、测试与验收的依据。

本平台由五个基于钉钉宜搭低代码平台构建的应用组成：

1. **天眼**——任务追踪与项目管理看板；
2. **大眼睛**——校园宣传与内容互动平台；
3. **开门**——移动端门禁控制应用；
4. **电子班牌集控**——电子班牌设备集中控制与内容投放系统；
5. **综合报表**——跨应用报表聚合门户。

本文档的编写目的具体包括：

- 向项目干系人（校方管理层、信息中心、开发团队、测试团队）清晰传达平台要解决的业务问题与预期形态；
- 为开发与配置工作提供可执行的功能规格，明确每个子系统的功能边界、数据模型、业务流程与权限模型；
- 为测试团队提供可验证的验收标准；
- 为后续迭代提供需求基线，控制需求漂移。

### 1.2 项目范围

本平台覆盖校园运营中的"监控"与"信息"两大主题：

- **监控域**：对学校任务执行情况（天眼）、物理空间出入（开门）、信息展示终端（电子班牌集控）进行集中监控与控制；
- **信息域**：对校园宣传内容（大眼睛）与跨业务数据视图（综合报表）进行统一生产、分发与汇聚。

## 2. 产品愿景与定位

### 2.1 背景与问题陈述

安徽钉钉学校在日常运营中面临以下典型问题：

1. **任务布置靠口头、执行靠记忆。** 校长办公会、行政例会上布置的工作事项散落在会议记录、微信群聊与口头交代中，缺少统一的登记、指派、审批与追踪载体。管理层无法回答"现在有多少事在推进、卡在谁手上、被什么阻滞"这三个基本问题。跨校区的任务（集团化办学场景下需要外出到其他学校执行）更是缺乏占用时间与行程的可视化。

2. **校园宣传内容生产与分发割裂。** 校园新闻、教学教程、学生艺术作品分别发布在公众号、美篇、微信群等不同渠道，缺少一个面向全体师生与家长的统一内容阵地。学生作品缺乏展示与激励机制，创作积极性难以持续。

3. **门禁管理依赖物理钥匙与人工值守。** 特定场景（访客接待、夜间出入、应急通行）下需要远程、可追溯的开门手段，而传统门禁不具备移动端授权控制能力。

4. **电子班牌"有屏无内容"。** 教室门口的电子班牌硬件已部署，但内容更新依赖 U 盘拷贝或单机操作，无法做到"管理端一次发布、全部终端即时更新"。

5. **业务数据散落在各应用中，管理层缺少统一观察入口。** 随着数字化应用增多，校长需要打开多个应用分别查看报表，缺少一个按权限、按重要性组织的报表门户。

本平台正是针对上述五类问题的一体化解决方案。

### 2.2 产品定位

本平台定位为**学校数字化运营的基础设施层**：

- 对**事**：天眼让每一件事"有出处、有责任人、有审批、有状态、有看板"；
- 对**内容**：大眼睛让校园内容"有阵地、有互动、有激励"；
- 对**空间**：开门让物理出入"有授权、有记录"；
- 对**终端**：电子班牌集控让信息发布"有集控、有轮播、有配置"；
- 对**数据**：综合报表让管理视角"有门户、有注册、有排序"。

五个子系统彼此独立又互为支撑：天眼产生的运营数据与大眼睛产生的内容数据，都可以通过综合报表门户被管理层统一消费；大眼睛的内容可以投放到电子班牌终端；天眼的通知与外勤动态构成首页的运营脉搏。

### 2.3 目标用户画像

#### 2.3.1 校长/集团管理层（决策者）

- **典型特征**：关注全局态势，时间碎片化，习惯在手机上获取信息；
- **核心诉求**：一眼看清全校任务推进态势（大盘）、随时查看关键业务报表（综合报表）、掌握来访接待安排（外勤预告）；
- **使用频率**：每日多次短时访问。

#### 2.3.2 行政管理人员（办公室/教务处）

- **典型特征**：任务的发起者与协调者，同时是校园宣传内容的主要生产者；
- **核心诉求**：快速创建并指派任务、跟踪催办；发布校园新闻与通知；管理电子班牌投放内容；
- **使用频率**：每日高频使用。

#### 2.3.3 教师（执行者/创作者）

- **典型特征**：任务的执行人，同时是教程、帖子、学生作品的指导者；
- **核心诉求**：清楚知道自己待办的事项（小盘）、完成任务并消除阻滞；便捷发表内容与指导学生作品投稿；
- **使用频率**：每日查看，按需操作。

#### 2.3.4 IT 管理员（信息中心）

- **典型特征**：负责设备接入、凭证管理、权限配置；
- **核心诉求**：管理门禁设备凭证（APP_ID/SECRET_KEY/TEAM_ID/设备序列号）、维护电子班牌播放列表与刷新配置、注册报表门户页面；
- **使用频率**：按需配置，故障时高频。

#### 2.3.5 学生与家长（受众/参与者）

- **典型特征**：内容的消费者，学生同时是艺术作品的创作者；
- **核心诉求**：浏览校园新闻、查看班级作品、为同学的作品点赞；
- **使用频率**：每周数次。

#### 2.3.6 安保/值班人员（开门使用者）

- **典型特征**：在门岗、值班室等点位使用移动端开门；
- **核心诉求**：一键可靠开门，操作简单不卡顿；
- **使用频率**：按需，突发场景下要求秒级响应。

### 2.4 核心价值主张

| 维度 | 现状痛点 | 平台价值 |
|------|----------|----------|
| 任务管理 | 事项散落、责任不清、无法追溯 | 任务项目化、流程化，双层看板全局透视 |
| 校园宣传 | 渠道分散、互动缺失 | 统一内容阵地，点赞排行激励创作 |
| 门禁通行 | 依赖钥匙、无法远程 | 手机一键开门，云端授权 |
| 信息发布 | 单机维护、更新滞后 | 集中控制、定时轮播、500ms 级配置热更新 |
| 数据消费 | 报表分散、入口混乱 | 注册制门户，按权重排序一站式访问 |

### 2.5 成功指标（KPI）

| 编号 | 指标 | 目标值 | 度量方式 |
|------|------|--------|----------|
| KPI-1 | 行政事项任务线上化率 | ≥ 90% | 线上任务数 / (线上 + 抽样统计的线下任务数) |
| KPI-2 | 任务按期完成率 | ≥ 85% | 期望完成时间内完结的任务占比 |
| KPI-3 | 阻滞任务平均滞留时长 | ≤ 3 个工作日 | 阻滞状态持续时长的均值 |

| KPI-6 | 开门操作成功率 | ≥ 99% | 成功开门指令 / 总指令 |

## 3. 用户场景分析

本章以叙事方式刻画各角色在真实校园场景下与平台的交互，作为第 4 章功能需求的来源依据。

### 3.1 场景一：校长在周一例会后追踪任务落地（天眼）

周一上午，校长办公会确定了本周五项重点工作。会后，办公室主任打开钉钉中的"天眼"应用首页，页面顶部滚动播放着未过期的通知公告（每 5 秒切换一条），下方实时显示当前时间。主任点击"发起任务"，选择目标学校（集团下属某校区）、勾选任务标签（如"教学视导"），填写任务描述。富文本正文的前几段会被系统自动提取为摘要，便于看板上一眼识别。系统自动为任务计算默认期望完成时间（次日），主任调整后指定执行人，提交进入审批流程，任务审批人确认无误后点击同意。

任务生效后，被指派的执行人打开天眼首页，在"我待做的"列表中看到这条新任务；点击行内"查看"按钮，直接跳转到流程详情页处理。执行过程中若遇到困难，执行人在任务上标记"阻滞"并说明原因。审批人若看到任务仍处于阻滞状态，点击同意时系统会拦截并提示"您没有解决阻滞！"，强制要求先排除障碍再推进——这保证了管理层在大盘上看到的"已完成"都是真正完成的任务。

周五，校长打开"大盘"报表查看本周任务全景：多少在运行、多少已完成、哪些被阻滞、分布在哪些学校与标签下。若想看某位中层干部的个人执行情况，则打开"小盘"，指定执行人与最后推动日期，即可看到该成员名下运行中的任务及指定日期内被推动过的任务，且外勤类任务会被自动过滤，避免外出行程干扰工作量判断。

### 3.2 场景二：来访接待预告自动呈现（天眼·外勤）

集团将于本周接待兄弟学校来访交流。接待负责人在天眼中创建一条带"外勤"属性的任务，填写参与成员、来访学校名称、占用日期与占用时间段（如上午/下午）。

该信息随即出现在天眼首页的"来访动态"区域：系统自动提取未来 7 天内（并保留结束后 1 天内以"【已结束】"标注）的外勤任务，拼接成"某某、某某将于 8 月 7 日（周五）上午访问××学校。"的预告文案。任何打开天眼首页的成员都能在第一时间掌握近期来访安排，无需在群里反复询问。

### 3.3 场景三：宣传干事发布校园新闻（大眼睛）

校园艺术节落幕，宣传干事打开大眼睛的"写新闻"表单，填写标题、正文并上传现场照片（支持多张）。提交后，新闻进入内容库。师生打开大眼睛首页，最新 6 条新闻以卡片形式呈现：标题、发布日期、作者头像、40 字内的导语摘要与封面缩略图。点击卡片跳转到新闻详情页。

同一套内容生产机制还支撑"写教程"（支持封面图 + 多个附件，适合课件资料分发）与"写帖子"（需选择年级、班级与分类，是班级圈与学生作品投稿的载体）。

### 3.4 场景四：班主任带学生参加艺术作品打榜（大眼睛·艺术专区）

美术课后，三年级二班的班主任指导学生上传绘画作品：打开"写帖子"，选择年级（三年级）、班级（二班）、分类（绘画），填写作品标题与创作说明，上传作品照片。

家长打开"艺术"页面，依次选择年级、班级（类别可选），页面加载该班最近 100 篇作品，每篇显示图片、标题、作者与点赞数。页面提供"作品"与"排行"两种浏览模式：作品模式按时间呈现，排行模式按点赞数降序排列。切换按钮带 500ms 防抖锁，避免快速连点造成重复加载；当用户从后台切回前台时页面自动刷新，保证点赞数据是最新的。

家长为孩子的作品点赞；再次点击同一作品则取消点赞。每位用户对同一作品只能保留一条点赞记录（系统按"作品实例 ID + 用户"定位已有点赞并删除）。点赞数即时变化并给予"感谢你的点赞~"/"已取消点赞"反馈。

说明：详情页的评论功能代码已具备（可读取与写入评论记录），但当前以"评论功能暂不开放~"策略性关闭，待内容安全审核机制就绪后再开放，属于受控的灰度决策而非缺陷。

### 3.5 场景五：值班保安夜间为访客远程开门（开门）

晚上九点，有预约的维修人员抵达校门口。值班保安打开手机钉钉中的"开门"应用，页面加载移动端调试控制台便于信息中心远程排障。保安点击"开门"按钮，应用使用预置的平台凭证向门禁云服务发起两步调用：先用 APP_ID 与 SECRET_KEY 换取访问令牌，再携带令牌向门禁控制接口发送开门指令（含 TEAM_ID 与设备序列号）。门锁应声开启，全程不超过数秒，且无需保安持有任何物理钥匙。

### 3.6 场景六：信息中心统一更新全校电子班牌内容（电子班牌集控）

开学季，信息中心需要在全校电子班牌上轮播新学期宣传海报。管理员先在"发布"表单中上传若干海报图片并登记标题（系统为每张图片分配 UUID）。再打开"客户配置"，选择目标终端，从图片库中勾选组成循环播放列表，设置刷新周期（如每 6 秒切换一张），并可勾选强制全屏播放。

各班级的电子班牌屏幕以浏览器方式打开"客户"播放页：页面启动时先加载终端配置（播放列表、切换间隔、是否强制全屏），随后进入轮播循环；与此同时，配置加载器每 500ms 轮询一次远端配置——管理员在管理端的任何修改，终端最迟 500ms 内即可感知并生效，无需重启屏幕。若配置开启强制全屏，页面自动请求全屏显示，避免学生误触退出。

### 3.7 场景七：校长一站式查看全局报表（综合报表）

学期末，校长需要查看教学、德育、后勤等各条线的报表。无需记忆十几个报表地址，只需打开"综合报表"应用：门户页加载"可供访问的页面"注册表中的全部条目，按权重从高到低排列，以图标 + 应用名 + 介绍的形式陈列。校长点击任一卡片即跳转到对应报表。

信息中心新增一份报表时，只需在注册表中新增一条记录：填写图标地址、应用名、介绍、报表地址与权重。门户下次加载即自动呈现，无需任何代码改动——这就是页面注册制带来的可扩展性。

### 4.1 子系统一：天眼（任务追踪与项目管理）

#### 4.1.1 功能概述

天眼是平台的运营中枢，解决"学校事项执行不可见、不可控、不可追溯"的问题。其核心设计为：

- **项目制组织**：任务必须挂靠"学校 + 任务标签"组合（即项目），保证每件事有归属；
- **流程化管控**：任务不是普通表单，而是审批流程实例，指派与推进需经审批人确认；
- **阻滞强制消除**：审批通过前必须消除阻滞标记，杜绝"带病完成"；
- **双层看板**：大盘（report 报表）面向管理层做全局统计，小盘（display 页面）面向个人按执行人 + 日期过滤；
- **外勤行程预告**：外勤类任务自动汇聚为首页来访动态，服务集团化办学的跨校协同；
- **通知轮播**：通知公告带有效期，首页滚动播放，过期自动下线。

#### 4.1.5 业务流程

**流程一：任务全生命周期**

```
[分配人] 创建任务（选学校、标签、执行人、期望完成时间）
    │   富文本正文 → 自动提取摘要；选学校 → 回填学校名称快照
    ▼
提交 → 进入审批流程（任务审批人节点）
    │
    ├─ 审批人审阅：若阻滞≠无，点击同意被拦截 → 退回执行人排除阻滞
    │
    ▼
审批通过 → 任务生效（状态：运行中）
    │
    ├─ 执行人处理：首页"我待做的"可见 → 查看详情 → 推进（更新流程）
    ├─ 管理层监控：大盘全局统计 / 小盘按人按日核查
    ▼
任务完结（状态：已完成）
```

**流程二：外勤接待登记**

```
[接待负责人] 创建任务 → 勾选"外勤"属性
    → 填写参与成员、来访学校名称、占用日期、占用时间段
    → 提交并生效
        │
        ▼
天眼首页自动纳入"外勤预告"（窗口：-3天 ~ +7天）
    → 占用日期 +1 天后标注【已结束】，窗口外自动消失
```

**流程三：通知公告发布**

```
[管理员] 新增通知（内容 + 可选链接 + 有效期/长期有效）
    → 保存即生效
        │
        ▼
天眼首页每 5 秒轮播未过期通知；点击跳转链接
    → 到期自动停止展示（无需人工下线）
```

### 4.2 子系统二：大眼睛（校园宣传与内容平台）

#### 4.2.1 功能概述

大眼睛是校园的统一内容阵地，解决"宣传渠道分散、师生创作无展示、互动激励缺失"的问题。平台承载三类内容：

- **新闻**：学校官方资讯（活动报道、通知公告的图文版）；
- **教程**：教学资源与操作指南，支持附件分发；
- **帖子**：带年级/班级归属的图文内容，是学生作品投稿与班级圈的核心载体。

### 4.4 子系统四：电子班牌集控（终端集中控制）

#### 4.4.1 功能概述

电子班牌集控解决"班牌内容更新靠单机、无法集中管控"的问题。系统采用"发布—配置—播放"三层结构：

- **发布**：图片素材库，每张图片一个 UUID、标题与图像；
- **客户配置**：面向终端（"客户"即一台受控屏幕）的播放策略：循环播放列表（关联多张已发布图片）、刷新周期（秒）、强制全屏开关；
- **客户**：终端播放页，以浏览器全屏方式按配置轮播图片，并以 500ms 级频率热加载配置。

该架构的关键特征是**拉模式（pull）集控**：终端不接收推送，而是高频轮询云端配置。任何配置变更无需逐台操作、无需重启，即可在秒级内扩散到全部终端。

- 「客户」播放页需要允许匿名或设备账号常驻访问（班牌终端通常以固定账号或免登方式打开），但应限制其仅能读取，不可编辑；

- 建议为每台终端建立"终端—配置"一一对应关系登记，避免误配到其他终端（当前以单配置记录承载，属演进项）。

### 4.5 子系统五：综合报表（跨应用报表门户）

#### 4.5.1 功能概述

综合报表解决"报表散落各应用、管理层访问路径碎片化"的问题。其核心机制是**页面注册制**：门户本身不生产数据，而是维护一张"可供访问的页面"注册表（图标、应用名、介绍、报表地址、权重）；门户页加载注册表并按权重降序陈列，点击即跳转。

门户页内置了平台统一的 QuickMap 数据访问层（ORM 封装：select/insert/update/delete + 自动分页 + CSRF 令牌携带 + 结构化并发重试），体现本平台"一套数据访问基座、多应用复用"的技术路线。

#### 4.5.2 页面清单

| 序号 | 页面名称 | formUuid | 类型 | 定位 |
|------|----------|----------|------|------|
| 1 | 报表 | `FORM-BD71E9CC16FC4D91B91D1BE8341FCDA88BN3` | display | 报表门户：按权重陈列已注册页面 |
| 2 | 可供访问的页面 | `FORM-BFACAC88CDE74D1C8F3C05A9425ED9F51WY6` | receipt | 页面注册表 |

#### 4.5.3 数据模型

**实体：注册页面（RegisteredPage）**

| 字段 | 组件 | 必填 | 说明 |
|------|------|------|------|
| 图标地址 | TextField | 是 | 页面卡片图标 URL |
| 应用名 | TextField | 是 | 报表所属应用的展示名 |
| 介绍 | TextareaField | 否 | 一句话说明报表内容 |
| 报表地址 | TextField | 是 | 目标报表 URL（宜搭报表页或外链） |
| 权重 | NumberField | 是 | 排序值，门户按权重降序展示 |
#### 4.5.4 功能清单

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| FR-BB-01 | 页面注册 | 管理员新增/修改/删除注册条目（图标、应用名、介绍、报表地址、权重） | P0 |
| FR-BB-02 | 门户陈列 | 门户页加载全部注册条目，按权重降序排列，以"图标 + 应用名 + 介绍"卡片呈现 | P0 |
| FR-BB-03 | 一键跳转 | 点击卡片跳转至报表地址（新窗口打开），实现跨应用报表直达 | P0 |
| FR-BB-04 | 跨应用取数能力 | 门户内置 QuickMap ORM 的 AppMapper 跨应用访问模式，为后续在门户内直接聚合其他应用数据（而非仅链接跳转）预留能力 | P2 |
| FR-BB-05 | 注册条目校验 | 报表地址应为合法 URL；权重为数值；应用名非空（宜搭必填校验 + 提交前检查） | P1 |

#### 4.5.5 业务流程

```
[信息中心] 在「可供访问的页面」登记新报表：
    图标地址 / 应用名 / 介绍 / 报表地址 / 权重
        │
        ▼
[管理层] 打开「报表」门户
    → 门户加载注册表 → 按权重降序渲染卡片
    → 点击卡片 → 新窗口打开对应报表
```

运营规则：

- 权重以 10 为步长分配（如 100、90、80），便于后续插入调整；
- 报表下线时直接删除注册条目，门户即时收敛；
- 同一报表地址不得重复注册（提交前人工核查，系统级唯一性校验为演进项）。

#### 4.5.6 权限模型

| 角色 | 门户浏览 | 跳转报表 | 注册表维护 |
|------|----------|----------|------------|
| 校长/管理层 | 是 | 是 | 否 |
| 行政人员 | 是（按条目可见性） | 是 | 否 |
| 信息中心 | 是 | 是 | 是 |

权限实现要点：

- 门户页面对全体教职工可见，但注册表编辑仅限信息中心；
- 报表本身的数据权限由各来源应用自行控制，门户只负责导航，不承担数据级授权；
- 如需对不同角色展示不同报表集合，演进方向为在注册表增加"可见角色"字段（远期需求，不在本期范围）。

### 6.4 数据流向

**流向一：任务数据流**

```
创建(任务表单) → 流程引擎(审批) → 实例库(RUNNING/COMPLETED)
    ├─→ 首页待办(按执行人/发起人过滤)
    ├─→ 小盘(按执行人+修改日期过滤、去重、剔外勤)
    ├─→ 大盘(report 聚合统计)
    └─→ 外勤任务 → 首页外勤预告(时间窗口过滤)
```

**流向二：内容数据流**

```
投稿(写新闻/写教程/写帖子) → 内容库
    ├─→ 首页(最新6条/频道)
    ├─→ 艺术页(年级×班级×类别筛选 + 点赞聚合)
    ├─→ 帖子详情(图集 + 点赞 + 评论读取)
    └─→ 互动写回：赞/评论 insert/delete → 内容库关联记录
```

**流向三：集控数据流（拉模式）**

```
素材发布 → 素材库
配置编排 → 客户配置(播放列表/周期/全屏)
    ↓ 终端每500ms轮询
客户播放页 → 过滤素材 → 轮播渲染
```

**流向四：报表导航流**

```
注册表(登记URL+权重) → 门户(降序渲染) → 用户点击 → 目标报表(各应用自治数据权限)
```

### 6.5 数据生命周期与清理策略

| 数据 | 生命周期 | 清理策略 |
|------|----------|----------|
| 任务流程实例 | 长期保留（审计需要） | 不删除；已完成任务归档保留 |
| 通知 | 展示期=有效期；过期不删除 | 每季度人工清理过期通知 |
| 外勤任务 | 窗口内展示（-3天~+7天） | 窗口外自动不展示，数据保留 |
| 赞/评论 | 随帖子存续 | 帖子删除后孤儿记录由管理员定期清理 |
| 素材 | 长期保留 | 下线素材从播放列表移除，不物理删除 |
| 注册页面 | 随报表存续 | 报表下线即删除条目 |

### 7.2 INT-01/02 钉钉消息与组织集成

- **身份**：五个应用均以钉钉登录态为前提，员工字段（EmployeeField）直接映射钉钉通讯录成员；
- **任务消息**：天眼任务为流程表单，指派与审批节点通过宜搭流程引擎自动产生钉钉待办与通知消息，执行人在钉钉「待办」中可直接进入任务详情；
- **管理后台数据源**：大眼睛管理后台通过 `getTodoTasks`（待办）、`getMySubmmit`（我创建的）、`getNotifyMeTasks`（抄送我的）三个远程数据源对接宜搭任务中心接口。

### 7.3 INT-03 门禁硬件对接（EZCloud）

**对接对象**：宇视科技 EZCloud 开放平台（`ezcloud.uniview.com`）。

**接口 1：令牌换发**

```
POST https://ezcloud.uniview.com/openapi/user/app/token/get
Content-Type: application/json
Body: { "appId": "<APP_ID>", "secretKey": "<SECRET_KEY>" }
Response: { "data": { "accessToken": "<token>" } }
```

**接口 2：门禁控制**

```
POST https://ezcloud.uniview.com/openAPI/acs/v1/device/door/control
Content-Type: application/json
Authorization: <accessToken>
Body: { "teamId": "<TEAM_ID>", "command": 1, "deviceSerial": "<DEVICE_SERIAL>" }
```

**对接约束**：

- `command: 1` 表示开门指令；如未来需要关门、常开、常闭等指令，应扩展为指令字典；
- accessToken 具有时效性，当前实现为每次开门现取令牌（简单可靠但有两次往返开销）；演进方向为令牌缓存复用；
- 必须落实 SEC-01 凭证后端化整改后方可扩大授权范围。

### 7.4 INT-04/05 跨应用取数与基础数据注入

- **QuickMap ORM**：平台统一的数据访问层，封装宜搭 `searchFormDatas`（表单查询）与 `getInstances`（流程实例查询）接口，自动分页（每页 100 条循环取数）、自动携带 CSRF 令牌、结构化并发重试；
- **AppMapper 跨应用模式**：以目标应用 appKey 构造 AppMapper 即可跨应用读取数据，为综合报表门户未来从"链接导航"升级为"数据聚合"提供通道；
- **Infection 注入**：年级/班级下拉选项从平台基础配置动态注入（`Infection.Grade.of().infect(控件).setOptions().setDefaultValue()`），保证大眼睛帖子归属选项与全校组织架构一致；
- **天眼首页的跨表读取**：通知表与任务流程实例均在首页被读取拼装，依赖 QuickMap 的流程查询模式（asProcess）。

| latest.js | `cdn.ahkdxx.cn/yida-dev-bundle/dist/latest.js` | 大眼睛、开门、班牌工具集（QuickMap、Infection 等） |
| vConsole | `unpkg.com/vconsole@latest` | 开门页端内调试面板 |

依赖风险与对策：CDN 不可用时页面核心功能退化（天眼首页无法加载待办）。对策为基座脚本加载失败时给出可感知提示，并评估将基座内联或迁移至稳定 CDN。

### 7.6 跨应用报表聚合（门户演进路线）

- **现状（本期）**：综合报表为链接导航型门户，注册表记录 URL，点击跳转；
- **演进（下期）**：利用 QuickMap AppMapper 跨应用取数，在门户页内直接渲染各应用关键指标卡片（如：天眼运行中任务数、大眼睛本周新增内容数），实现真正的"聚合"而非"导航"。
